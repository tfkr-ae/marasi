# Marasi

Marasi is a local HTTP/HTTPS intercepting proxy. A service instance owns a proxy listener and an open project. The project is a `.marasi` SQLite database containing captured traffic and assessment evidence.

## Select the instance and project

Use `marasi` on PATH. Read `marasi --help` for the installed version's commands and default config directory.

Carry the same `--config-dir` and `--instance` on every command in a session. The default instance is `default`. Prefer `--json` for structured output and check the exit code before consuming it. Commands that write certificate or artifact bytes need their normal output mode instead.

Inspect existing instances before starting or changing one:

```sh
marasi --config-dir "$CONFIG_DIR" service list --json
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" service status --json
```

Set `CONFIG_DIR` to the intended config directory and `INSTANCE` to the intended instance name. Before making changes, confirm that status identifies the intended `instance` and absolute `project` path. Use an existing instance only when the user has selected it.

Status also reports the instance's API level as the integer `api` (`api:` in human output, after `version:`). It goes up only when a route, request field, response field or event that clients rely on is removed or changes meaning; new routes, fields and events never raise it. To decide whether a client supports an instance, compare `api`, not `version`. An instance older than API levels has no `api` field, and human output has no `api:` line.

For a new session, choose an unused instance name and the intended project. A project has an exclusive lock, so concurrent instances need different projects. Keep a custom config directory short and absolute. The control socket path `<config-dir>/instances/<instance>.sock`, including its terminating byte, must fit within 104 bytes.

```sh
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" service start \
  --project-name "$PROJECT" --address 127.0.0.1 --port 0 --json
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" service status --json
```

Set `PROJECT` to the chosen project name. `--project-name` selects `<config-dir>/projects/<name>.marasi`. Use `--project /absolute/path/project.marasi` instead for a file elsewhere. These selectors are mutually exclusive. `--port 0` assigns a free port. Start launches a detached service with its listener already running.

To let a client that cannot open the socket, such as a GUI in a webview or a client on another machine, reach the control API, start the instance with a network address for its control listener, guarded by a control password you choose:

```sh
export MARASI_PASSWORD="$CONTROL_PASSWORD"
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" service start \
  --project-name "$PROJECT" --port 0 --control-address 127.0.0.1:0 --json
```

`--control-address HOST:PORT` serves the same control API over plain HTTP at that address; port `0` picks a free port. Read the bound address from `control_listener` in `service start --json` or `service status --json` (`null` when there is none; `control listener network address:` in human output). `--password` or `MARASI_PASSWORD` on `service start` sets the control password; prefer the variable, because a flag shows in `ps` and shell history. With a password, every request to the address must send it as `Authorization: Bearer PASSWORD` (the scheme name is case-insensitive); a missing or wrong password gets 401 `unauthorized` with `WWW-Authenticate: Bearer`, and a password in the query string is never accepted. A password cannot start or end with whitespace or contain control characters. Without a password, the address needs no authentication, but keeps websites in the user's browser out (see the no-password rules below), and an address beyond loopback is refused unless you pass `--no-password` (`control listener network address HOST:PORT is beyond loopback: set a control password with --password, or pass --no-password to run without one`; this holds for `MARASI_CONTROL_ADDRESS` too). `--no-password` on `service start` also wins over `MARASI_PASSWORD`. The socket never asks for the password. The password lives only in the instance's memory: `service start` and `service restart` hand it to the instance process through its environment, never its arguments, `service restart` keeps it, and stopping the instance forgets it. Nothing is written to disk, and an old `<instance>.token` file is ignored. Status, list, events, and logs never show the password; do not print it where the user did not ask for it. A non-loopback address writes a warning in the instance log, and on stderr when stderr is a terminal, because the address has no TLS. With no password, one more warning line goes to stderr, `--json` included, and to the instance log: on loopback `warning: control listener network address ADDR has no control password; any local process can control the instance`, beyond loopback `...; any host that can reach it can control the instance`. An address already in use fails the start.

**No-password rules.** These apply only while the instance has no control password; with one, any `Origin` is echoed and any `Host` is accepted.

- A request with no `Origin`, such as from curl, a script, or a GUI's native side, is accepted.
- A request whose `Origin` is not allowed is refused with 403 `origin_not_allowed`, `origin ORIGIN is not allowed without a control password: set a control password, or allow the origin with --allow-origin`, and no CORS headers. A preflight from such an origin is refused the same way; one from an allowed origin is answered with 204 and the CORS headers, including `Access-Control-Max-Age: 600`, so a browser reuses it for 10 minutes per URL.
- `--allow-origin ORIGIN` (repeatable, or comma-separated) and `MARASI_ALLOW_ORIGIN` (comma-separated) set the allowed origins on `service start`, `service control start`, and `service control update`. An origin is `SCHEME://HOST[:PORT]` with no path, such as `http://localhost:5173`, or `null`; anything else is `invalid_origin`. Allowing `null` is accepted with a warning on stderr and in the instance log, because a sandboxed iframe or a local file on any site sends it. `update` replaces the whole list, and `--allow-origin ''` clears it; without the flag or variable the list is kept. `service restart` keeps it.
- The `Host` header must be an IP or `localhost`; the port is not checked, so a published container port or an SSH tunnel works. Bound to a specific IP, that IP is accepted, plus `localhost` on loopback. Bound to a wildcard address such as `0.0.0.0`, any IP and `localhost` are accepted. Anything else is 421 `host_mismatch`: a hostname gets `the Host header names a hostname, which a web page can rebind to this machine: use the IP address, or set a control password`.

To change the network address of a running instance, use `service control start --address HOST --port PORT`, `service control update --address HOST --port PORT`, `service control stop`, and `service control status` (routes `POST /service/control-listener/start|update|stop` and `GET /service/control-listener/status`; the start and update body is `{"address":HOST,"port":PORT}` plus an optional `"password":PASSWORD` or `"no_password":true`, and an optional `"allowed_origins":[...]`). `start` requires both flags; `update` takes both or neither, and port `0` picks a free port. Each prints the status (`status`, `control_listener`, `password_set`, `allowed_origins`) with `--json`; `password_set` says whether a control password guards the address, and human `service control status` prints it as `password: set` or `password: none`, then `allowed origins: A, B` or `allowed origins: none`; `control_listener` is `null` when the address is stopped, and a stopped address remembers no endpoint, so `start` must name one again. `start` on an active address is `listener_already_active`; `update` or `stop` on a stopped one is `listener_inactive`. An address in use or a host that cannot bind is `listener_unavailable` with the reason, and leaves the previous address serving. While a restart hands the address over, `update` and `stop` are `restart_in_progress`. Without a password flag, the control password stays the same across start, update, and stop, and the socket stays available throughout. Stop and update close every connection and event stream on the old address; a request that made the change on that address gets its response first. Start and update write the non-loopback warning too, and the no-password warning when they bind an address with no password or remove it. Starting or moving the address beyond loopback with no password is refused with `password_required` unless the command passes `--no-password`, even when the instance already has no password. `update --allow-origin` alone changes only the allowed origins. Events: `control_listener.started`, `control_listener.updated`, and `control_listener.stopped`, each with `status`, `control_listener`, `password_set`, and `allowed_origins`.

To set, change, or remove the control password while the instance runs, pass `--password PASSWORD` or `--no-password` (not both) to `service control start` or `service control update`; an empty `--password ''` is a usage error, never `--no-password`, here and on `service start`; `update` needs no `--address` and `--port` to change only the password. Over the socket, `MARASI_PASSWORD` is the default for that `--password`, and `--no-password` wins over it. Over `--remote`, `MARASI_PASSWORD` is the current password that authenticates the command, and only `--password` on the subcommand sets a new one, so rotate a remote instance with:

```sh
MARASI_PASSWORD="$OLD_PASSWORD" marasi --remote "$URL" service control update --password "$NEW_PASSWORD"
```

With no `--password`, `--no-password`, or (over the socket) `MARASI_PASSWORD`, `update` keeps the current password, and `update` with nothing to change is a usage error. A change closes every network connection and event stream that authenticated with the old password, at once; the request that made the change gets its response, then its connection closes. The old password then gets 401. Setting the password the instance already holds changes nothing. After `--no-password`, requests with no `Authorization` header succeed and `password_set` is `false`. A change emits `control_listener.updated`, and `service restart` hands the current password, not the one the instance started with, to the successor. An invalid password is refused with `invalid_password`.

For Pairing, which hands another device the network address and password to connect with, run `service control pair`. It prints a QR code of the JSON payload `{"url","password","instance"}` on stdout, then a blank line and the URL as text; `--json` prints only the payload. `password` is present only when one is set, so the human output shows the password inside the QR code: run it only when the user asks to pair a device. Locally the payload comes from `GET /service/control-listener/pairing`, which only the socket serves; on the network address it is 403 `socket_only`. With no network address running, the route is 409 `listener_inactive` and the command fails with `start one with marasi service control start --address HOST --port PORT`. On a wildcard address such as `0.0.0.0`, `url` uses the IP of the interface on the default route. `--host HOST` replaces the host in `url` and keeps the port, for an address the scanning device can reach, such as a VPN IP. A hostname in `--host` is refused when the instance has no password, because the address then accepts only an IP as the `Host`. With `--remote`, the payload is the remote URL, the password the CLI holds when the instance has one, and the instance name from `service status`.

Proceed only when status reports `running`, the intended instance and project, and a non-empty `proxy_listener`. To switch projects on a selected instance, use `project open --name NAME` or `project open --path PATH`, then confirm the new project with `service status`.

`service status` also reports `run_id` (`run id:` in human output): an opaque value that the instance process draws when it starts. It stays the same for the life of that process and changes on every start, including a `service stop` and `service start`, a `service restart`, or a restart after a crash. When `run_id` differs from the last value you read, the instance restarted, so read again any state you cached from it. Compare it only for equality; do not parse it.

### Set flags from the environment

These environment variables set a flag when the flag is not passed. Each flag's `--help` names its variable as `(env MARASI_X)`. An empty variable counts as unset.

| Variable | Flag | Commands |
| --- | --- | --- |
| `MARASI_CONFIG_DIR` | `--config-dir` | every command |
| `MARASI_INSTANCE` | `--instance` | every command |
| `MARASI_REMOTE` | `--remote` | every command except `service start` and `service list` |
| `MARASI_PASSWORD` | `--password` | `service start`, and `service control start` and `update` over the socket, set it on the instance; any command sends it with `--remote` |
| `MARASI_PROJECT` | `--project` | `service start` |
| `MARASI_PROJECT_NAME` | `--project-name` | `service start` |
| `MARASI_ADDRESS` | `--address` | `service start` |
| `MARASI_PORT` | `--port` | `service start` |
| `MARASI_CONTROL_ADDRESS` | `--control-address` | `service start` |
| `MARASI_ALLOW_ORIGIN` | `--allow-origin` (comma-separated) | `service start`, `service control start`, `service control update` |

Precedence is the flag, then its variable, then the built-in default. A passed flag also ignores the variable it conflicts with: `--project-name` ignores `MARASI_PROJECT`, `--project` ignores `MARASI_PROJECT_NAME`, `--instance` ignores `MARASI_REMOTE`, and `--remote` ignores `MARASI_INSTANCE`. Two conflicting variables with no flag to settle them are a usage error that names both, such as `MARASI_PROJECT and MARASI_PROJECT_NAME cannot be used together: unset one`; the same holds for `MARASI_REMOTE` with `MARASI_INSTANCE`. Two conflicting flags stay a usage error. A value the flag would refuse fails as `invalid MARASI_X "VALUE"`. There is no `MARASI_JSON`: pass `--json` on each command that needs it.

### Drive an instance on another machine

To drive an instance whose control listener has a network address, point the CLI at that address with `--remote URL` instead of `--instance`:

```sh
export MARASI_PASSWORD="$CONTROL_PASSWORD"
marasi --remote "http://$CONTROL_ADDRESS" service status --json
marasi --remote "http://$CONTROL_ADDRESS" traffic list --json
```

`--remote` takes an `http` or `https` URL (`https` for a TLS reverse proxy in front of the address; a path in the URL prefixes every request), and `MARASI_REMOTE` sets it for the shell session; `--remote` wins over `MARASI_REMOTE`. The control password comes from `--password` or else `MARASI_PASSWORD`, and is sent as `Authorization: Bearer`; with neither, no `Authorization` header is sent, which an instance without a password accepts. `--remote` together with `--instance` is a usage error, and so is `MARASI_REMOTE` together with `MARASI_INSTANCE`; `--instance` ignores `MARASI_REMOTE`. A wrong password fails with `control password rejected by URL: check --password or MARASI_PASSWORD`, a missing one with `control password rejected by URL: the instance needs one: pass --password or set MARASI_PASSWORD`, and an address nothing answers at with `no instance answers at URL`. The local socket-path limit does not apply. Commands that only call the control API, `events`, and `service restart` behave and print exactly as they do through the socket, `--json` included. `service start` and `service list` act on this machine and refuse a remote. `service stop` sends the stop and returns once the instance stops answering at the URL: the connection is refused, or a reverse proxy answers in its place, such as with 502.

With a password, the instance accepts any `Host` header, so a hostname, a VPN name, a reverse proxy, or a container name all work. Without a password, it accepts only an IP or `localhost` as `Host` (see the no-password rules) and answers 421 `host_mismatch` to a hostname, so a TLS reverse proxy in front of it must send the bound IP as `Host`, for example nginx `proxy_set_header Host 127.0.0.1:PORT;`. `service restart` hands the network address and the control password to the successor, so the URL and password keep working. The address and the proxy listener stay bound throughout, so a new connection during the handover waits for the successor instead of being refused; a request already in flight on the old instance can still fail, so retry it. On Windows the address is bound again, and a request during the handover can be refused.

A browser GUI can call a network address with a password from any origin, or one without a password from an origin allowed with `--allow-origin`: the instance echoes the request `Origin` and never allows credentials, so send the control password as `Authorization: Bearer PASSWORD` on every request, and read `GET /events` with a `fetch` stream rather than `EventSource`, which cannot send that header. To resume that stream, send the last event id as `Last-Event-ID`.

The instance and the CLI run on different machines, so read their output as the instance machine sees it:

- Printed addresses, such as the proxy listener and the CDP endpoint from `chrome start --cdp`, are the instance machine's. A loopback address there is not reachable from the CLI's machine.
- `listener interfaces` lists the instance machine's addresses, loopback included, to choose a `listener start` or `listener update` `--address` from (`--json`: `items` of `address`, `family` `ipv4` or `ipv6`, `interface`; IPv4 first, then by interface and address). A link-local IPv6 address carries its zone, such as `fe80::1%eth0`.
- `service status` reports the instance machine's operating system (`os:`; `os` in `--json`). Over a remote, `chrome path add` and `chrome path remove` default `--os` to it, so a path is tagged for the machine that runs Chrome. Pass `--os` to override.
- Over a remote, `service status` adds this CLI's version and API level (`cli version:` and `cli api:`; `cli_version` and `cli_api` in `--json`) beside the instance's `version` and `api`. When the API levels differ it prints `warning: this marasi speaks API level N but the instance speaks API level M` on stderr, or `... but the instance reports no API level` for an instance older than API levels; under `--json` that text goes in the `warning` field. Differing versions with the same API level do not warn. Commands still run; update the side with the lower level if a command or field is missing or behaves differently. No other command checks versions or API levels.

Over `--remote`, `wordlist add PATH` and `report template add PATH` read `PATH` on this machine, upload its contents under its base name, and delete the local file only after the instance accepts it, so add still moves the file. A refused upload (`wordlist_already_exists`, `report_template_already_exists`, an invalid name such as a hidden template name) or an instance that does not answer leaves the local file in place. The instance publishes `wordlist.added` or `report.template.added` as for a local add. Without a remote, both commands send the path and the instance moves the file itself.

Over `--remote`, project paths and names refer to the instance machine. `project list` lists the instance's `<config-dir>/projects`, with the same rows and `--json` shape as a local list there. `project open --path PATH` sends `PATH` unchanged, so it must be an absolute path on the instance machine; a relative path is refused with `invalid_project_request`. `project open --name NAME` is resolved in the instance's config directory, which creates its projects directory if needed; nothing is created on this machine. Without a remote, `project list` reads this machine's config directory and needs no running instance.

## Capture and inspect traffic

Set `PROXY_LISTENER` from status, not from the requested port.

For HTTP capture:

```sh
curl --noproxy '' --proxy "http://$PROXY_LISTENER" "$TARGET_URL"
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" traffic list \
  -q "host = \"$TARGET_HOST\" AND path = \"$PATH_PREFIX*\"" --limit 20 --json
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" traffic get "$REQUEST_ID" --json
```

Set `TARGET_HOST` to the captured request's exact host and `PATH_PREFIX` to its path prefix. Set `REQUEST_ID` from the matching list entry. `--noproxy ''` prevents curl's `NO_PROXY` settings from bypassing the proxy, including for localhost.

For HTTPS, fetch the running instance's loaded CA and give it to the client:

```sh
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" certificate get > "$CA_FILE"
curl --noproxy '' --proxy "http://$PROXY_LISTENER" --cacert "$CA_FILE" "$TARGET_URL"
```

Set `CA_FILE` to a session-owned file. Prefer client-specific trust over changing the system trust store.

## Show a stored response in a browser

To let the user see how a captured response renders, give them `http://marasi/view/$REQUEST_ID` to open in a browser that uses the proxy listener. Marasi redirects to the pair's original URL, and the browser's next request there, within 10 seconds, gets the stored response unchanged, without reaching the origin. Everything the page then loads goes to the live site and is captured. The URL takes the pair UUID, not its number. A plain-text 404 means no pair has that UUID in the open project; 409 means the pair has no response yet or is a WebSocket upgrade. A browser view can replace the browser's cookies with the stored `Set-Cookie`. `http://marasi/cert` serves the CA certificate in DER form through the same listener.

`traffic list` returns the newest page of traffic, oldest first within the page, so the newest pair is the last row. Follow `next_cursor` with `--cursor` for older pages, keeping the same query and passing the first page's `as_of` with `--as-of`. Cursors are opaque tokens; `--backward` with `prev_cursor` walks back toward newer pairs. `--exclude 'image/*'` (repeatable) hides content types; pairs with no content type yet always stay. Each pair has a `number`, its `#` in capture order; `-q 'number = 10'` finds one. `--order-by` sorts by one of `requested_at`, `number`, `method`, `host`, `path`, `status_code`, `content_type`, `length`, `client_protocol` or `origin_protocol`, with optional `desc`, for example `--order-by 'length desc'`; pairs with no response sort last, and every page needs the same `--order-by`. `launchpad get --order-by` sorts entries the same way. In JSON, `request.raw` and `response.raw` are base64. Decode them before inspection or editing. A pair carried over HTTP/2 is stored as text: the request line `GET /path HTTP/2`, then each other pseudo-header field as its own line (`:authority: example.com`) where it came on the wire, then the fields in wire order; the response starts `HTTP/2 200`. Skip lines that start with `:` when you read it as HTTP/1.

A capture is complete when `traffic get` returns the matching request and response. A client response alone does not prove that Marasi captured the exchange.

## Drive a browser with CDP

To automate a browser, attach to the one Marasi starts:

```sh
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" chrome start --profile "$CHROME_PROFILE" --cdp --json
```

Set `CHROME_PROFILE` to the chrome profile, or omit `--profile` to use `default-profile`; any other chrome profile must be registered first (`chrome --help`). The JSON holds `profile` and a `cdp` object with `http`, `ws` and `reused`. Pass `cdp.http` to Playwright's `chromium.connectOverCDP` or Puppeteer's `connect({ browserURL })`; use `cdp.ws` for a raw CDP client. `reused: true` means the chrome profile was already running with that CDP endpoint, so it can carry another session's tabs and cookies.

Run the same command again whenever you need the CDP endpoint later: it returns the live CDP endpoint for that chrome profile, marked `reused`, and opens a new window in it.

Error `chrome_running_without_cdp` means the chrome profile is already open without a CDP endpoint, and CDP cannot be turned on in a running Chrome. Ask the user to close that chrome profile, then run `chrome start --cdp` again, or start a different chrome profile with `--cdp`.

Marasi's proxy switches, quiet switches and certificate trust reach Chrome only through `marasi chrome start`. Start every browser you drive with it, never by running Chrome yourself with copied switches.

## Search traffic

`traffic list -q` takes an AIP-160 query over a fixed set of fields. `traffic list --help` lists the fields and the operators each one accepts. Marasi supports only part of AIP-160:

- Header and body text, notes and metadata use `:` (contains, ignoring case). Text terms need at least 3 characters. Bare text searches all of them.
- `host`, `method`, `scheme`, `path` and `content_type` use `=` or `!=` with exact case. A `*` at the start or end of the value matches anything there.
- `upstream_proxy` matches the name of the upstream proxy that carried the pair, with `=` or `!=` and exact case: `upstream_proxy = "burp"`. `upstream_proxy = ""` matches pairs sent directly. A pair records its route when its response is stored, including the upstream proxy a failed request tried. `traffic get` shows it as `upstream_proxy: NAME (scheme://host:port)` or `upstream_proxy: direct`, and JSON pair reads, traffic list items (`traffic list --json` and the other pair lists) and `traffic.response` events carry `upstream_proxy` as `{"name", "address"}`, or `null` for a pair with no response yet or one captured before routes were recorded. The snapshot never holds credentials and does not change when the upstream proxy is later updated or removed.
- `client_protocol` and `origin_protocol` match the protocol a pair used between the client and Marasi, and between Marasi and the origin: `http/1.1` or `h2`, with `=` or `!=`, for example `client_protocol = "h2"`. HTTP/2 over TLS and cleartext HTTP/2 by prior knowledge are both `h2`. The two differ only when Marasi translated the pair between versions. Pairs captured before protocols were recorded are `http/1.1`. `traffic get` prints `client_protocol:` and `origin_protocol:` lines after `scheme:`; the human `traffic list` (and the other pair lists) has a `PROTOCOL` column showing one protocol, or `CLIENT->ORIGIN` when they differ. JSON pair reads and traffic list items carry `client_protocol` and `origin_protocol`; `traffic.request` events carry both, and `traffic.response` events carry `origin_protocol` when the pair reached the origin.
- `id` matches a pair by its id, a quoted UUID, with `=` or `!=`: `id = "01937f5d-351a-7e68-936d-61a7a25661a3"`. A UUID must be quoted wherever a query takes one.
- `status_code`, `length` (the stored response body's length in bytes, chunked responses included, decoded for gzip or br) and the timestamps take comparisons. Timestamps are quoted RFC 3339.
- `metadata.<key>` compares the JSON value at that key and is type-strict. Quote strings, but leave booleans and numbers bare.
- `launchpad` is launchpad membership. `launchpad = "<launchpad id>"` matches pairs in that launchpad, `launchpad != "<launchpad id>"` matches pairs not in it, including pairs in no launchpad, and `launchpad:*` matches pairs in any launchpad. It finds linked captured traffic as well as launched pairs, which `metadata.launchpad_id` does not.

```sh
-q 'status_code >= 500 AND host = "*.example.com"'
-q 'response_body:"password" OR response_head:"set-cookie"'
-q 'launchpad:* AND response_body:"token"'
-q 'metadata.launch.status = "cancelled"'
-q 'method = "POST" AND (path = "/api/*" OR path = "/graphql")'
```

OR binds tighter than AND, so `a AND b OR c` means `a AND (b OR c)`. Add parentheses whenever you mix them.

In JSON, `index.complete: false` means the search index is still being built. Text searches can miss older traffic until it reports `true`. Do not treat an empty text search as proof of absence while it is `false`.

## Task map

Use the listed command group's `--help`, then the chosen subcommand's `--help` for flags.

| Task | Command group | Guidance |
| --- | --- | --- |
| Expose, move, or close the control API's network address | `service control` | `start` requires both `--address` and `--port`. `update` takes both or neither, so it can change only the password or the allowed origins; without `--allow-origin` it keeps the allowed origins, and `--allow-origin ''` clears them. `pair` prints a QR code for Pairing another device. The socket keeps working whatever the network address does. See [Select the instance and project](#select-the-instance-and-project). |
| Change listener address or pause capture | `listener` | `start` and `update` require both `--address` and `--port`; `interfaces` lists the addresses the instance machine can bind. Stopping the listener leaves the service running. |
| Find named project files | `project list` | Lists projects under the selected config directory, or with `--remote` under the instance machine's. Each row has the file's modification time in UTC (`MODIFIED`, `modified_at` in RFC 3339); a symlinked project shows its target's. |
| Annotate captured traffic | `notes`, `traffic metadata` | Metadata updates replace the JSON rather than merge it. |
| Change or delete many pairs | `traffic bulk` | `highlight`, `link`, `unlink`, `metadata set`/`clear`, `note append`/`clear`, `delete`. Select with `--id` (repeatable) or `--ids-file` (`-` for stdin), or `-q` with the list page's `--as-of`. Bulk metadata sets one dotted key and leaves the rest. Nothing asks for confirmation, and `delete` also removes notes, links, and logs. |

| Read, inject into or cancel a gRPC call or event stream | `stream messages`, `stream get`, `stream inject`, `stream cancel` | On HTTP/2 and HTTP/1.1, a pair whose request or response head names a message framing by its `content-type` is a streamed pair: `application/grpc*` (`grpc`), `application/grpc-web*` (`grpc-web`; base64 `application/grpc-web-text` is read whole), `application/connect+*` (`connect`), and in responses only `text/event-stream` (`sse`) and `application/x-ndjson` or `application/jsonl` (`ndjson`). On HTTP/1.1 the body may be chunked, length-framed or read until the origin closes; each message goes on in a chunk of its own when the head that went out is chunked, and chunked trailers are kept. Unary Connect (`application/proto`, `application/json`) and anything else stays an ordinary pair, whatever its path, and so does an `sse` or `ndjson` response whose `Content-Encoding` is anything but gzip or deflate, or that declares a `Content-Length` with one. An `sse` or `ndjson` response with a gzip or deflate `Content-Encoding` is inflated as it arrives and compressed again toward the client by Marasi, flushed after each message: its messages are stored, hooked and held decoded (`compressed` false), and the client gets the same messages in different compressed bytes. One that cannot be inflated is stored as the compressed bytes received for the message, `compressed` true, with `metadata.encoding` and `metadata.inflate_error`; one that inflates past `stream_max_message_size` is stored the same way, its `inflate_error` starting `too large`, with `metadata.too_large`. Either resets both legs (`INTERNAL_ERROR`, or `ENHANCE_YOUR_CALM` when too large) and writes a `WARN` proxy log naming the pair. Each stream message goes on as soon as it is whole, unchanged, and is stored as its own stream message with its own UUID: a gRPC, gRPC-Web or Connect envelope (a gRPC-Web trailers frame, flag `0x80`, and a Connect end-of-stream message, flag `0x02`, included), a server-sent event up to its blank line, or an NDJSON line. HTTP/1.1 has no reset: wherever a reset is described here, an HTTP/1.1 leg's connection is closed instead, and a client that closes its connection cancels the pair. The pair is stored with its heads and empty bodies; `metadata.streamed.request` and `metadata.streamed.response` give each streamed direction's `framing`, `messages` count, `ending` (`complete`, `cancelled`, `reset` with `reset_code`, or `cut short`) and `trailers` (`grpc-status` among them). `stream messages <pair-id>` pages both directions together, oldest first (`--limit`, `--cursor` set to the last ID shown; `next_cursor=` on stderr when more remain). `stream get <pair-id> <message-id>` prints one, ending with `text:` and its text form when it has one (`text` with `--json`, null when it has none). A protobuf message (`application/grpc`, `+proto`, gRPC-Web or `application/connect+proto`) is decoded without a schema into protoscope text, one field per line with its wire type: `1:VARINT 150`, `2:LEN {"a string"}`, `3:LEN {` and a nested message, `4:LEN {1 2 3}` (packed varints), ``5:LEN {`fffe`}`` (bytes), `6:I32 1i32`, `7:I64 1i64`, `8:SGROUP` … `8:EGROUP`. `long-form:N` marks a tag, varint or length sent N bytes longer than it needs, so the text keeps the exact bytes. A payload that is not protobuf is one hex literal, and so is a message nested more than 100 levels deep, from that depth on; `--text` refuses braces nested more than 100 levels deep. A `+json` codec's text form is the payload as text; server-sent events and NDJSON have none. Watch a call live with `events` (stored pairs only): `streamed_pair.started` (`pair_id`, `framings`: each direction already known to be streamed, such as `{"request":"grpc"}`; a direction recognised later shows on its messages and in the end) when the first head naming a framing is read; `stream_message` for each message once whole, cut short or too large, with the `stream get --json` fields but `text`, plus `payload_truncated`: past 64 KiB `payload` is `null` and `payload_truncated` is `true`, so read it with `stream get`; `stream_message.progress` (`pair_id`, `direction`, `framing`, `bytes` arrived so far, envelope included; no payload) at most every 100 ms per direction while a message is still arriving; and `streamed_pair.ended` (`pair_id`, `directions`: each direction as in `metadata.streamed`, `trailers` and so `grpc-status` included) once every direction ended, after `traffic.response`. With `--json`, `payload` is base64 of the message without its 5-byte envelope, and `flags` is the envelope's flags byte (bit 0 is compression); an event's or line's `payload` is all its bytes, line endings included, and its `flags` is `null` (`-` in human output). A gRPC or gRPC-Web message with the compressed flag (`grpc-encoding`), or a Connect one (`connect-content-encoding`), has `compressed` true and `metadata.encoding`; with gzip or deflate its `payload` is stored decompressed and has a text form, and it goes on as its original compressed bytes. Any other encoding is stored as the compressed bytes, with no text form, and cannot be edited. A message edited by an extension goes out uncompressed with its compressed flag cleared and is stored with `compressed` false and `metadata.edited`. A compressed message that fails to decompress, or decompresses past `stream_max_message_size`, is stored as its compressed bytes with `metadata.inflate_error` (starting `too large` for the latter), the stream is reset on both legs (`INTERNAL_ERROR`, or `ENHANCE_YOUR_CALM` when too large) and a `WARN` proxy log names the pair. A message the origin reset or cut partway through is stored with what arrived and `metadata.cut_short`. One over `stream_max_message_size` in `marasi_config.yaml` (bytes, 64 MiB when unset) is stored empty with `metadata.too_large` and `metadata.size_seen`, the stream is reset on both legs with `ENHANCE_YOUR_CALM`, and a `WARN` proxy log names the pair. Hold and edit them with `checkpoint`; extensions see and edit them through `processStreamMessage` (see `extension api streammsg`). `stream inject <pair-id> --direction request|response` sends a new stream message into a running streamed pair: `request` toward the origin, `response` toward the client. Its payload is the bytes of `--file`, or piped stdin, or empty; for `grpc`, `grpc-web` and `connect` it is the message without its envelope, and Marasi adds the envelope; for `sse` and `ndjson` it goes out as given, so end it with a blank line or a newline. It goes out between two of the sender's messages, never inside one: while the sender is partway through a message, the injection waits for it. It runs the `processStreamMessage` hooks and Checkpoint like any message (a held one makes the command wait until it is forwarded or dropped), and is stored and announced with `metadata.injected`. `--compress auto` (the default) compresses it with the direction's `grpc-encoding` or `connect-content-encoding` when that is gzip or deflate, setting the compressed flag; `--compress never` sends it uncompressed. With `--text`, the file or stdin is the message's text form, as `stream get` shows it, and Marasi encodes it with the direction's codec (protoscope text for protobuf, the text for `+json`); text that does not parse is refused with `invalid_stream_request` and its `line L column C`, and nothing is sent, as is `--text` into a direction with no text form. It prints `stream message <id> injected` on stderr, or with `--json` the stored message as `stream get --json` gives it without `text`. An injection into a direction that is not streamed, has not started, or ended, or into a pair that is not running, is refused with `stream_not_open` and the reason; one into a direction whose head carries `Content-Length` (no chunked coding on HTTP/1.1) with `stream_inject_refused`. An unknown pair is `not_found`. `stream cancel <pair-id>` ends a running streamed pair on both legs, `RST_STREAM CANCEL` on HTTP/2 and closing both connections on HTTP/1.1, records each direction still going as `cancelled`, and abandons its held messages; it prints `stream <pair-id> cancelled` (`{"pair_id","cancelled":true}` with `--json`), and a pair no longer running is `stream_not_open`. A project switch, a restart or a service stop cancels every running streamed pair the same way, and stores what it carried in the project it started in. A streamed response whose head arrives after a project switch is answered with a 502 and is not carried or stored. Routes: `POST /stream/{pair_id}/inject` with `{"direction","payload":base64 | "text":string,"compress"?:"auto"|"never"}` (one of `payload` and `text`), and `POST /stream/{pair_id}/cancel`. |

## Write Lua extensions

An extension is Lua source stored in the project. The proxy calls the hooks the source defines: `startup` when it loads, and `processRequest`, `processResponse`, `processWebSocketMessage`, and `processStreamMessage` (each message of a streamed pair, such as a gRPC call; type `streammsg`) for traffic. On a stream whose head declares a length, a hook's change to that length, or a drop, is ignored and a proxy log says why. Only the `checkpoint` extension's `intercept*` hooks decide what Checkpoint holds; `interceptStreamMessage` runs after the `processStreamMessage` hooks, and `message:text()` gives a stream message's text form, the same text `stream get` and Checkpoint show; `message:set_text(text)` encodes an edited text form into the payload, and raises with the line and column for text that does not parse (wrap it in `pcall` to recover). `extension call` runs any global function. Read the API for the installed version before you write Lua, then read each library or type you use:

```sh
marasi extension api
marasi extension api marasi.repo
marasi extension api req
```

Call library functions and object methods with `:`, for example `marasi.strings:upper(s)` and `request:method()`. A call with `.` passes the wrong arguments. The sandbox has no `string`, `io`, or `os` library. `drop()` stops a request, response, or message from being sent on. A Lua error in a hook is logged and the item continues. A hook interrupted by a project switch, service stop, or client disconnect drops the item.

Replace the source with `extension update`, which runs it at once and stores it only if the run succeeds. A failed run keeps the previous source and publishes no `extension.updated`, though any Lua that ran before the error stays in effect until the project reopens. A failed run or `extension call` is refused with `lua_error` and the Lua error, such as `lua_error: [string "..."]:3: attempt to call a nil value`. Then check `extension logs` and the affected traffic. While an extension is enabled, `events` also shows each print line as `extension.log`, and each `marasi.gui:render` and `marasi.gui:update` call as `extension.gui.rendered` and `extension.gui.updated`. `extension ui UUID` prints what the extension last drew per target (not toasts) and its last UI state per key, for a client that joins later.

An extension can also ship a web component for its UI tab by setting the string globals `ui_code` and `version`. `extension get` prints only the Lua source; `extension get UUID --json` adds `ui_code` and `version`, read from the running Lua, each `""` when the extension sets none. A successful `extension update` publishes `extension.updated` with the extension's `id`; reread `extension get --json` then, because the web component may have changed. The update runs in the extension's existing Lua state, so a global the new source no longer sets keeps its old value until the project reopens: set `ui_code = ""` to clear it.

## Verify and finish

After each change, read the affected record or status. After a launch, run `traffic get <launch_id>` and check `metadata.launch.status`: `completed`, `cancelled`, or `failed` with a `metadata.launch.reason`. After an Armory run, inspect the resulting captured traffic. After report export or artifact download, inspect the output file. Report the instance, project, relevant IDs, and output paths, or the failed command and its error.

Stop event subscribers you started. Cancel detached launches you started that you no longer need. Resolve held Checkpoint items and restore interception settings you changed. Stop only a service this session started, unless the user requests otherwise:

```sh
marasi --config-dir "$CONFIG_DIR" --instance "$INSTANCE" service stop --json
```

Preserve project databases and exported evidence. Remove only temporary files created by this session.
