# Launchpad

Users group captured traffic into named launchpads in the open project and fire a raw HTTP working copy tagged with that pad.

## Sub-features

- Create an empty pad with `launchpad create --name`.
- List pads oldest first with `launchpad list`, each with its entry count and the status code of its newest entry.
- Read one pad and its linked traffic in entry order with `launchpad get`, narrowed by a traffic query with `-q` or `--query`, or sorted by `--order-by`.
- Search traffic by launchpad membership with the `launchpad` query field: `traffic list -q 'launchpad = "<id>"'`, `launchpad != "<id>"`, or `launchpad:*`.
- Rename or describe a pad with `launchpad update`.
- Attach an existing request UUID with `launchpad link --request`, and detach it with `launchpad unlink PAD_ID REQUEST_ID`.
- Reorder entries with `launchpad move PAD_ID REQUEST_ID... [--before REQUEST_ID]`, or move them to another pad with `--target PAD_ID`.
- Link or unlink many pairs to a launchpad, finding, or test case with `traffic bulk link` and `traffic bulk unlink`.
- Launch a working copy with `launchpad launch --scheme` and `--raw-file` or piped stdin, waiting for its final record by default or returning at once with `--detach`.
- List pending launches with `launchpad pending`.
- Read one launch, pending or finished, with `launchpad status`.
- Cancel a pending launch by its launch id with `launchpad cancel`.
- Keep a pending launch's pair in its launchpad: unlinking it, deleting it, or deleting its pad is refused until the launch finishes.
- Choose human-readable or `--json` output.

## How to get to it (user POV)

Start a service first. Run `dist/marasi --config-dir "$VERIFY_CONFIG_DIR" --instance "$VERIFY_INSTANCE" launchpad create --name Login`. Link a traffic id from `traffic list` when you want a pad member. Launch by piping a raw HTTP request or passing `--raw-file`.

## Driving it with shell and curl

Run `launchpad create --name Login --description variants --json` and save `id`. Run `launchpad list --json` and require that id with `"entry_count":0,"last_status_code":null`; human `launchpad list` prints the row as `$PAD_ID  Login  variants  0  -`. Run `launchpad update "$PAD_ID" --description edited --json`. Link a captured request with `launchpad link "$PAD_ID" --request "$TRAFFIC_ID" --json`. Pipe `GET /launchpad-proof.txt HTTP/1.1` with CRLF or LF line endings, a `Host` of the local origin, and a blank line to `launchpad launch "$PAD_ID" --scheme http --detach --json` and require `{"launch_id":"…","status":"pending"}`. Save `launch_id`. Retry `launchpad get "$PAD_ID" --json` until it contains both the linked id and a new `/launchpad-proof.txt` row whose id is the launch id. Confirm that launched path with `traffic list -q 'path = "/launchpad-proof.txt"' --json`. Retry until that row's `metadata` is `{"launch":{"status":"completed"},"launchpad":true,"launchpad_id":"$PAD_ID"}`. `traffic list -q 'metadata.launch.status = "completed"' --json` must return it. `launchpad list --json` must then show the pad with `"entry_count":2` and the launched row's status code in `last_status_code`. `traffic list -q 'metadata.launchpad = true' --json` and `-q "metadata.launchpad_id = \"$PAD_ID\""` must return it, and `-q 'metadata.launchpad = "true"'` must not, because the stored value is a JSON boolean.

To prove launchpad queries, run `traffic list -q "launchpad = \"$PAD_ID\"" --json` and require exactly the linked id and the launch id. `-q 'launchpad:*'` must return both once each, even when one is also linked to a second pad, and `-q "launchpad != \"$PAD_ID\""` must return neither but must return a captured request that is in no pad. `launchpad get "$PAD_ID" -q 'path = "/launchpad-proof.txt"' --json` must return only the launch id in `items`. `launchpad get "$PAD_ID" -q 'launchpad = "nope"'` must exit 1 with `getting launchpad: invalid_query: "nope" is not a launchpad id; use a launchpad UUID at position 13`.

To prove cancel, serve an origin path that never answers, launch it, and save `launch_id`. `launchpad pending --json` must list `{"launch_id":"$LAUNCH_ID","launchpad_id":"$PAD_ID","status":"pending"}` in `items`, and human `launchpad pending` must print one row of `$LAUNCH_ID`, `$PAD_ID`, and `pending` between the `LAUNCH ID  LAUNCHPAD ID  STATUS` column-name lines. `launchpad status "$LAUNCH_ID" --json` must return that pending record. Run `launchpad cancel "$LAUNCH_ID" --json` and require `{"launch_id":"$LAUNCH_ID","launchpad_id":"$PAD_ID","status":"cancelled"}`. Retry `traffic list -q 'metadata.launch.status = "cancelled"' --json` until it returns the launch id with no response. Run the same cancel again: it must exit 1 with `{"error":"cancelling launch: launch_finished: launch $LAUNCH_ID is cancelled"}`. A random UUID must exit 1 with `cancelling launch: not_found`. After the cancel, `launchpad status "$LAUNCH_ID"` must exit 0 and print `status: cancelled`, and `launchpad pending --json` must return `{"items":[]}` (human mode prints nothing). `launchpad status` on a random UUID must exit 1 with `reading launch: not_found`.

## Gotchas

- `--name` is required on create and must be non-empty. Update requires `--name` or `--description`.
- Launch needs `--scheme http` or `https`, and either `--raw-file` or piped stdin. A TTY stdin fails. The raw bytes must be parseable HTTP with a non-empty `Host` and a header/body blank line. CRLF works; LF-only is accepted.
- The working copy is the raw bytes you supply. Linked members are not launched and are not required to launch.
- Without `--detach`, the CLI polls `GET /launch/{id}` and prints the final record. A failed launch exits 1 with `launching launchpad request: launch $LAUNCH_ID failed (upstream_error)` (or another reason), in `{"error":…}` under `--json`. SIGINT or SIGTERM while waiting cancels the launch and exits 0 with the cancelled record. In human mode both status lines (`launch $LAUNCH_ID pending` and the final one) go to stderr and stdout is empty, so `$(…)` captures nothing; use `--json` to capture the record.
- A `project open` to a different project while a launch is pending interrupts it. The launch ends `failed` with reason `interrupted`, its row and `metadata.launch` are stored in the original project, and `launch.failed` is published before `project.opened`. A launch held at Checkpoint publishes `checkpoint.dropped` before `launch.failed`. A waiting `launchpad launch` exits 1 with `launching launchpad request: launch $LAUNCH_ID failed (interrupted)`. `GET /launch/{id}` and `launchpad cancel` still find the launch after the switch, because the service keeps its most recent 1024 finished launches in memory for the life of the process; `launchpad cancel` exits 1 with `launch_finished: launch $LAUNCH_ID is failed (interrupted)`.
- `POST /launchpad/{id}/launch` and `--detach` return `{"launch_id":"…","status":"pending"}` as soon as the launch is accepted, before the round trip, and `launch.started` is published. `GET /launch` lists pending launches and `GET /launch/{id}` reads one while it is pending. The launch then ends as `completed`, `cancelled`, or `failed` (with a `reason`), published as `launch.completed`, `launch.cancelled`, or `launch.failed`, and the outcome is merged into the row's `metadata.launch`. Retry `launchpad get` and `traffic list` until the launched path and its `metadata.launch` appear.
- `launchpad status` exits 0 for any launch it finds, including `failed`; it is a read. Human mode prints `launch_id:`, `launchpad_id:`, `status:`, and `reason:` (when present) lines to stdout. `launchpad pending` prints rows of launch id, launchpad id, and status, with the column names above and below them.
- `launchpad list` prints headerless rows of id, name, description, entry count, and the newest entry's status code. Entries are linked request/response pairs; the newest is the newest by capture, wherever it sits in entry order. The status is `-` (`last_status_code` is `null` in `GET /launchpad` and `--json`) when the pad has no entries or its newest entry has no response (still in flight, or cancelled or failed); it never falls back to an older entry.
- `POST /launch/{id}/cancel` (`launchpad cancel`) works from any client, not just the one that launched. It cancels the proxy client's request, so the upstream round trip is abandoned and no response is stored. A finished launch returns 409 `{"error":"launch_finished",…}` with its final record, read from memory or, for an older launch, from the stored pair's `metadata.launch` in the open project. An id that is not a launch returns 404 `not_found`.
- A launch goes through the proxy listener, persists a new traffic row, and auto-links that row to the pad. The proxy client tags the request with an internal `x-marasi-launch-id` header. Marasi honors it only from its own client for a pending launch, uses it as the row id, sets the `launchpad` and `launchpad_id` metadata keys from the launch, and removes it before forwarding. The stored raw request does not contain it. The header from any other client is removed and ignored.
- Link and launch look up ids in the currently open project. After opening a different project, previous pads and request ids are not visible. Opening the current path does not hide them.
- Duplicate link of the same request to the same pad returns a conflict, and the entry keeps its place.
- `launchpad get` and `GET /launchpad/{id}` list entries in entry order, not capture order. Every entry a pad gains goes last: a launch when its row is written, `launchpad link`, and `traffic bulk link`, which adds its new pairs in capture order. Prove it by linking a newer captured pair first and an older one second with `launchpad link`: `launchpad get --json` lists the newer one first. `--order-by` (`?order_by=`) still sorts by that field instead. No output has a position or key field; the order of `items` is the only sign of entry order.
- `launchpad unlink "$PAD_ID" "$TRAFFIC_ID"` calls `DELETE /launchpad/{id}/link/{request_id}`, prints `request $TRAFFIC_ID unlinked from launchpad $PAD_ID successfully` on stderr, returns `{"launchpad_id","request_id"}` with `--json`, and publishes `launchpad.unlinked`. A pair that is not linked, or a missing pad, is 404 `not_found`. Both arguments must be UUIDs, checked before any request.
- `launchpad move "$PAD_ID" "$C" "$B" --before "$A"` calls `POST /launchpad/{id}/move` with `{"request_ids":[…],"target_launchpad_id":"$PAD_ID","before_request_id":"$A"}`, prints `2 entries moved to launchpad $PAD_ID successfully` on stderr (`1 entry` for one), and returns `{"source_launchpad_id","target_launchpad_id","request_ids"}` with `--json`, the moved ids in their new entry order. It publishes one `launchpad.entries_moved` with the same body. Prove it with a pad holding `A`, `B`, `C`, `D` in entry order: the move above makes `launchpad get --json` list `B`, `C`, `A`, `D`, because the moved entries keep their entry order whatever the argument order, and a repeated id counts once. Without `--before` (or `before_request_id`) they go after the last entry; `--before` the first entry puts them at the top. Only the moved entries change place, and repeating a move to the same spot keeps working. `target_launchpad_id` defaults to the pad in the path. A pair that is not an entry, or a missing pad, is 404 `not_found`; a `--before` entry that is not in the pad or is itself moved is 400 `invalid_placement` (human mode prints `moving launchpad entries: 400 Bad Request`). A refused move changes nothing and publishes nothing. No ids, or a bad id in the body, is 400 `invalid_launchpad_request`; the CLI checks every id is a UUID before any request. A pending launch's pair can be moved within its pad.
- `launchpad move "$PAD_ID" "$C" "$A" --target "$OTHER_ID" --before "$X"` moves entries to another pad in one transaction: `C` and `A` leave `$PAD_ID` and become entries of `$OTHER_ID` before its entry `X` (after its last entry without `--before`), in their `$PAD_ID` entry order, `A` then `C`. A move never copies: `launchpad get "$PAD_ID" --json` no longer lists them. Other entries in both pads keep their order. Stderr prints `2 entries moved to launchpad $OTHER_ID successfully`, and the one `launchpad.entries_moved` names `$PAD_ID` as `source_launchpad_id`, `$OTHER_ID` as `target_launchpad_id`, and the moved ids. The moved rows' metadata, `launchpad_id` included, is unchanged, so `metadata.launchpad_id` of a launched row still names the pad it was launched from (ADR-0049). Refusals, each changing nothing and publishing nothing: a target that already holds one of the pairs is 409 `already_linked`; a missing target or source pad is 404 `not_found`; a `--before` entry that is not in the target is 400 `invalid_placement`; a pair that is a pending launch is 409 `launch_pending` with the pending ids in `request_ids`, and the CLI exits 1 with `moving launchpad entries: launch_pending: launch pending: $LAUNCH_ID`. Once the launch finishes, the same move succeeds.
- While a launch is pending, its pair stays in its pad (ADR-0049). `launchpad unlink "$PAD_ID" "$LAUNCH_ID"`, `traffic bulk unlink --launchpad "$PAD_ID"` and `traffic bulk delete` with a selection that holds the launch's pair (by `--id` or by a query that matches it) are refused as a whole: the route answers 409 `{"error":"launch_pending","message":"launch pending: $LAUNCH_ID","request_ids":["$LAUNCH_ID"]}`, nothing changes, and no `launchpad.unlinked`, `traffic.changed` or `sitemap.changed` is published. The CLI exits 1 with `unlinking launchpad request: launch_pending: launch pending: $LAUNCH_ID` (or `unlinking traffic:` / `deleting traffic:`), in human mode too. Prove it with the never-answering origin from the cancel proof: launch, wait for its row in `launchpad get`, run the three commands, then `launchpad cancel` and run them again; they now succeed. Unlinking the pair from another pad it was also linked to is allowed, and so is deleting a selection that leaves the pending pair out. Deleting a pad while a launch from it is pending, even one whose row is not written yet, is refused with the same error by the Go `Proxy.DeleteLaunchpad` that marasi-app calls; the control API has no delete-pad route.
- `traffic bulk link` and `traffic bulk unlink` take exactly one of `--launchpad`, `--finding`, or `--test-case UUID` plus a selection, and print `N pairs linked` or `N pairs unlinked`. Prove it with two captured `/api/*` pairs: `traffic bulk link --launchpad "$PAD_ID" -q 'path = "/api/*"' --as-of "$AS_OF"` prints `2 pairs linked` and `traffic count -q "launchpad = \"$PAD_ID\""` prints `2`; `launchpad unlink` each pair and the count is `0`; link one by `--id` and `traffic bulk unlink --launchpad "$PAD_ID" --id "$ONE" --json` returns `{"count":1}`. The routes `POST /traffic/bulk/link` and `/traffic/bulk/unlink` take `{"selection":…, "launchpad_id"|"finding_id"|"test_case_id":…}` with exactly one target and return `{"count":n}`, counting only pairs whose link changed. A selection is `{"ids":[…]}` or `{"query":…,"exclusion":[…],"as_of":"<pair id>"}`; a query selection never touches a pair newer than `as_of`. A missing target is 404 `not_found`; a bad body is 400 `invalid_bulk_request`, `invalid_selection` or `invalid_query`.
- The `launchpad` query field reads links, not metadata, so it finds linked captured traffic, which has no `launchpad_id` metadata. The value must be a quoted launchpad UUID; anything else, and any operator other than `=`, `!=`, and `:*`, is a 400 `invalid_query` with a position. `GET /launchpad/{id}?q=` keeps entries in entry order, and checks that the pad exists before it reads the query, so a missing pad is 404 `not_found` even with an invalid `q`.
