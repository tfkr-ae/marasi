# Armory

Users store raw HTTP templates in the open project, create runs against those templates with named wordlists, and fire the generated requests through the active proxy listener.

## Sub-features

- Create a template with `armory template create --name` and optional `--description` / `--raw-file` / `--framing`.
- Build a template from a captured pair's request with `armory template create --from-pair PAIR_ID`. A gRPC, gRPC-Web or Connect call becomes a **message-form body** with that framing.
- List templates oldest first with `armory template list`.
- Read one template with `armory template get`.
- Change name, description, raw template, or framing with `armory template update`.
- Delete a template with `armory template delete`.
- Validate a raw template and attack type with `armory run validate`.
- Create a run with `armory run create --template` and `--attack-type`.
- List runs for one template with `armory run list --template`.
- List every run in the project with `armory run list`, optionally narrowed with `--status`.
- Read one run with `armory run get`.
- Start a draft run with `armory run start`.
- Cancel an in-progress run with `armory run cancel`.
- List a run's captured traffic with `armory run traffic`.
- List a run's failed attempts, requests it built but did not send, with `armory run failed-attempts`.
- Delete a run with `armory run delete`.
- Choose human-readable or `--json` output.

## How to get to it (user POV)

Start a service first. Put wordlist files in `$VERIFY_CONFIG_DIR/wordlists`, or move them there with `wordlist add`. Run `dist/marasi --config-dir "$VERIFY_CONFIG_DIR" --instance "$VERIFY_INSTANCE" armory template create --name Lifecycle --raw-file request.raw`. Create a run from that template id, then `armory run start`.

## Driving it with shell and curl

Write `$VERIFY_CONFIG_DIR/wordlists/users.txt` with one line `payload`. Write a raw template that is a complete request, including the header-terminating blank line: `GET /armory-@@x@@.txt HTTP/1.1`, a `Host` of the local origin, and a blank line. Use CRLF. Run `armory template create --name Lifecycle --description first --raw-file "$RAW" --json` and save `id`. Run `armory template list --json` and require that id. Run `armory template update "$TEMPLATE_ID" --description replay --json`. Pipe the same raw bytes to `armory run validate --attack-type harpoon --wordlist users.txt --http --json` and require `{"status":"ok"}`. Run `armory run create --template "$TEMPLATE_ID" --attack-type harpoon --wordlist users.txt --http --json` and require `status` `draft`. Run `armory run list --template "$TEMPLATE_ID" --json` and `armory run get "$RUN_ID" --json`. Run `armory run start "$RUN_ID" --json`. Retry `armory run traffic "$RUN_ID" --json` until it contains `/armory-payload.txt`. Run `armory run get "$RUN_ID" --json` until `status` is `complete`. Run `armory run delete "$RUN_ID" --json`, then `armory template delete "$TEMPLATE_ID" --json`. To prove cancel, start a second run against a slow origin, wait until the origin records the path and `status` is still `in_progress`, then `armory run cancel`. Retry `armory run get` until `status` is `cancelled`. `complete` or `failed` is not a cancel proof.

To prove a template built from a pair, capture a gRPC unary call through `proxy_listener` (the [streamed pair](streamed-pair.md) recipe's interop server, a request message `2:VARINT 4`). Run `armory template create --from-pair "$PAIR_ID" --json`. Require `name` `POST 127.0.0.1:<port> /grpc.testing.TestService/UnaryCall` (`METHOD host path`), `framing` `grpc`, and a `raw_template` that is the captured `HTTP/2` head with no `content-length`, then `--- message ---` and the message's protoscope text, `2:VARINT 4`, with no payload position. Human `template get` and `template list` print `framing: grpc`. Replace `4` with `@@4@@`, save it with `template update --raw-file`, write a wordlist `8` and `abc`, and run a harpoon `--http` run. It must finish `complete` with `progress` `{"entries":1,"failed_attempts":1}` and `template_framing` `grpc`. `armory run failed-attempts "$RUN_ID" --json` lists `abc` as `payloads` `[{"position":0,"value":"abc"}]` with an `error` such as `message 1: line 10 column 10: bad number "abc": text form syntax error`. `run traffic` holds only the `8` pair, with `grpc_status` 0, and `traffic request` on it ends with the fresh envelope `00 00000002 1008`. `events` shows `armory.failed_attempt.created`, and the last `armory.run.updated` carries that `progress`. A Connect unary pair (`application/proto` with `Connect-Protocol-Version: 1`) builds a template with `framing` `connect` and one `--- message ---`; its run sends the encoded message as the whole body with no envelope and a matching `Content-Length`.

## Gotchas

- Template `--name` is required and must be non-empty, unless `--from-pair` is set. `--from-pair` cannot be combined with `--name`, `--description`, `--raw-file` or `--framing`; cobra refuses that before any request, and an unknown pair is `not_found`. Rename the built template with `template update`. Update requires `--name`, `--description`, `--raw-file`, or `--framing`; `--framing ""` clears it.
- `--framing` is `grpc`, `grpc-web` or `connect`. With a framing, the body is a message-form body: each request message in its text form under a line reading exactly `--- message ---` (or `--- message compressed ---`), and each request a run sends re-encodes every message and builds a fresh envelope, so a payload of any length stays well formed. Saving is refused with `invalid_armory_request` and the reason, for example `the content type "text/plain" does not name the template's framing grpc`. Without `--framing` such a separator is ordinary text. `skills/marasi/SKILL.md` has the full message-form rules (escaping inside quoted protoscope strings, `raw`, compression, Connect unary).
- A payload that leaves a message unable to encode is a failed attempt: not sent, not a pair, so `run traffic` never lists it, and the run goes on and can still be `complete`. A run's `progress` counts `entries` (pairs stored) and `failed_attempts`; human `run get` and `run list` end with `entries:` and `failed_attempts:` lines, and human `failed-attempts` prints `payloads: 0="abc"` and `error:`. Deleting the run deletes its failed attempts (`failed-attempts` is then `not_found`).
- `--attack-type` is `harpoon`, `broadside`, `tandem`, or `maelstrom`. Matching ignores case. The stored value uses that spelling. `--wordlist` is repeatable and names files under `$VERIFY_CONFIG_DIR/wordlists`. The service creates that directory empty; it does not seed wordlist files. `wordlist add` moves a source file there.
- `--http` sends generated requests as HTTP. Omit it and Marasi uses HTTPS.
- `armory run create` accepts `--max-concurrent 1` through `100`. Omit it and the run uses `10`.
- Validate needs `--raw-file` or piped stdin. A TTY stdin fails. Create uses the stored template, not stdin. Validate and start reject a template that is not a complete HTTP request with a non-empty `Host` and a header-terminating blank line. A run also needs at least one payload position, written as `@@x@@` or an explicit Go-template declaration such as `{{.Payload 0 "x"}}`. Harpoon and broadside need exactly one wordlist; tandem and maelstrom need one wordlist per template position.
- `armory run list` without `--template` lists every run in the project, oldest first. `--status` is repeatable and takes comma-separated `draft`, `in_progress`, `complete`, `failed` or `cancelled`; any other value is `invalid_armory_request`. `--status in_progress` is exactly the in-memory active set, so prove it with one run held on a slow origin and one finished run in another template, then cancel and require an empty `{"items":[]}`. `--status` with `--template` is refused before any request. Traffic listing accepts `--limit` and `--cursor`, but rows are oldest first. `traffic list` pages newest remaining rows. Each `armory run traffic` page carries `"index":{"complete":bool}`, the same as `traffic list`.
- Start sends through the proxy listener and stamps `metadata.armory_run_id`. A one-payload harpoon can finish before you read `armory run get`. Retry get and traffic until the path appears.
- Cancel is gated on the in-memory active set, not on stored `status`. A run left `in_progress` by an instance that stopped mid-run is `cancelled`, with `finished_at` set, once a service opens its project again, so start fails with `not_a_draft` and cancel with `run_not_active`. To prove it, start a run against a slow origin, `kill -9` the PID that `pgrep -f -- "--config-dir $VERIFY_CONFIG_DIR "` prints, then `service start` the same `--project-name` and `armory run get`. With `--json` the error is `cancelling Armory run: run_not_active`. Human output is `cancelling Armory run: 409 Conflict` and does not include that code. Cancel signals the active run and returns immediately. The JSON body may still show `in_progress`. Retry `armory run get` until `status` is `cancelled`. A producer error, including a missing wordlist, is `failed`.
- A refused `armory run validate` or `armory run create` is `invalid_armory_request` with a `message` naming the cause, in human and `--json` output: `creating Armory run: invalid_armory_request: harpoon requires exactly one wordlist`. To prove it, create a harpoon run with two `--wordlist` flags. Body problems are named too, such as `max_concurrent must be a whole number from 1 to 100`.
- Duplicate start of an already started run fails. Templates and runs belong to the currently open project.
- Template and run mutations publish `armory.template.created`, `armory.template.updated`, `armory.template.deleted`, `armory.run.created`, `armory.run.updated` (with the run's `progress`), `armory.run.deleted`, and `armory.failed_attempt.created` for each failed attempt. Subscribe with `events` before the mutation; a fresh subscription replays nothing.
