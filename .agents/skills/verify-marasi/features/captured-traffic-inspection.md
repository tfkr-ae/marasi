# Captured traffic inspection

Users list stored request/response pairs and open one pair to inspect its metadata and raw HTTP messages.

## Sub-features

- List the newest page of traffic with `traffic list`. Each human row starts with the pair's number, the ledger's `#`, then its id.
- Narrow the list with an AIP-160 query, `-q` or `--query`. `traffic list --help` lists the fields: exact-case `=`/`!=` with `*` at either end on `host`, `method`, `scheme`, `path`, and `content_type`; comparisons on `number`, `status_code`, `requested_at`, and `responded_at`; type-strict `metadata.<key>`, and `metadata.<key>:*` for pairs that have the key with any value, including `null`; and case-insensitive `:` text search on `request_head`, `request_body`, `response_head`, `response_body`, `note`, and `metadata`, or bare text across all of them; and launchpad membership with `launchpad = "<launchpad id>"`, `launchpad != "<launchpad id>"` (which includes pairs in no launchpad), and `launchpad:*`; and sitemap subtrees with `sitemap = "<node name>"` and `sitemap != "<node name>"`, where an unknown name matches nothing; and highlights with `highlight = n` and `highlight != n` for n from 1 to 8 (`!=` includes pairs with no highlight), `highlight:*`, and `NOT highlight:*`. Combine with `AND`, `OR`, `NOT`, `-`, and parentheses.
- Comparisons on `length`, the response's `Content-Length` as a number. A response without the header has length 0; an in-flight pair has none and matches only `!=` and `NOT`.
- Sort with `--order-by` (`GET /traffic?order_by=`): one of `requested_at`, `number`, `method`, `host`, `path`, `status_code`, `content_type`, `length`, then optional `desc`. Default `requested_at desc`. `launchpad get --order-by` sorts a launchpad's entries the same way (default entry order).
- Limit page size and continue with `--cursor`.
- Read one pair by UUID with `traffic get "$TRAFFIC_ID"`. Its `--json` body has `prettified: {request, response}`, the proxy's prettified copies of the two messages, outside `metadata`.
- Read one pair's metadata with `traffic metadata get "$TRAFFIC_ID"`.
- Replace one pair's metadata with `traffic metadata update "$TRAFFIC_ID" --file` or piped stdin.
- Set or clear one metadata key on a selection with `traffic bulk metadata set KEY JSON` or `traffic bulk metadata clear KEY` plus a selection (`POST /traffic/bulk/metadata` with `{"selection":…,"key":"a.b","value":<any JSON>}` or `{"selection":…,"key":"a.b","clear":true}`). The JSON argument is checked before any request, so quote strings: `'"seen"'`. It returns `{"count":n}`, counting only pairs whose metadata changed, and leaves every other key as it was. Human output is `N pairs updated` on stderr.
- Count matching pairs with `traffic count [-q] [--exclude] [--as-of] [--after]` (`GET /traffic/count`). Human output is the number on stdout, with a trailing `+` when `capped`; `--after "$AS_OF"` counts pairs captured since a list page.
- Count pairs per response content type with `traffic types` (`GET /traffic/content-types`). Human rows are `content_type  count`, with `-` for pairs that have no content type yet.
- Walk the sitemap with `traffic sitemap [--node NAME] [-q TEXT --as-of UUID] [--exclude] [--limit] [--cursor]` (`GET /traffic/sitemap`). Human rows are `name  pairs  errors  +`, where `+` marks a node with children; `next_cursor=` goes to stderr.
- Read several sitemap levels in one call by repeating `--node` or passing `--scope all|matching` (`POST /traffic/sitemap/levels`). `--node ''` is the origins. Each level prints under `# <node>` (`# (origins)` for `''`, and `# <node> (missing)` when no node has that name), and each level is a table whose column names, `NAME  PAIRS  5XX  MATCHING  MATCHING 5XX  CHILDREN`, print above and below its rows, with `-` in the matching columns without `-q`. A level with no rows prints only its `#` line. With `-q`, `--scope matching` (the default) lists only children with matches, and `--scope all` lists every child with its matching counts. A level's `next_cursor=… node=…` goes to stderr; `--cursor` continues one level, so it takes a single `--node`.
- Check a query, exclusion and sort without running them with `traffic validate [-q] [--exclude] [--order-by]` (`GET /traffic/query`). Valid prints `query is valid` on stderr (`{"valid":true}` with `--json`) and exits 0; invalid exits 1 with `validating query: invalid_query: <message> at position N`.
- Delete a selection with `traffic bulk delete` plus a selection (`POST /traffic/bulk/delete {"selection":…}`). It does not ask first. It returns `{"count":n}`, the pairs deleted, and takes with each pair everything it owns: note, launchpad, finding, test case and Armory links, WebSocket connection and messages, proxy logs, search index rows, highlight, prettified copies, and sitemap counts. It does not refuse a pair that is evidence for a finding.
- Choose human-readable or `--json` output for `traffic list`, `traffic get`, and `traffic metadata update`. `traffic metadata get` always returns JSON, without `prettified-request` or `prettified-response`.
- Read each pair's number in `number` on every `traffic list --json` item, on `traffic get --json`, and on the `traffic.request` event. It is the pair's position in capture order, from 1. It never changes and is never reused, so deleted pairs leave gaps. `traffic get` prints `number: N` after `id:`.
- Read each pair's highlight, `null` or a number from 1 to 8, in `highlight` on every `traffic list --json` item and on `traffic get --json`. Human output does not show it. Set one with `traffic bulk highlight` (see events.md).

## How to get to it (user POV)

Send traffic through a running instance, then run `dist/marasi --config-dir "$VERIFY_CONFIG_DIR" --instance "$VERIFY_INSTANCE" traffic list`. Copy an ID from the list into `TRAFFIC_ID` and pass it to `traffic get`. Add list flags when narrowing a busy project.

## Driving it with shell and curl

Send two distinct proxied requests, for example `GET /proof.txt` returning 200 and `POST /other` returning 404. Run `traffic list -q "host = \"$HOST\" AND method = \"GET\" AND path = \"/proof*\" AND status_code = 200" --limit 1 --json` and require that one row. A `host` clause that omits the origin port, and a method/status pair that matches nothing, must return empty `items`. A query naming an unknown field, such as `-q 'stauts = 200'`, must fail with `invalid_query` and a position. A text query on part of the origin body, in other case, such as `-q 'response_body:"<FRAGMENT>"'`, must return the GET row, and the same fragment as `request_body:` must not. A text term under three characters, such as `-q '"ab"'`, must fail with `invalid_query`. `traffic list --limit 1 --json` is the newest row. Pass its `next_cursor` to a second `--limit 1` page and require the older row and `next_cursor` null. Run `traffic get "$TRAFFIC_ID" --json` and base64-decode `request.raw` and `response.raw`. Require the method, path, status, and origin body inside those bytes. For an origin that answers `{"b":2,"a":1}` as `application/json`, `prettified.response` is the status line and headers followed by the indented JSON with sorted keys, and `metadata` has neither `prettified-request` nor `prettified-response`. A copy is `null` when the body cannot be prettified, for example plain text or an empty body. `traffic metadata get` on a fresh row is `{}`. `traffic metadata update --file` with `{"phase":"two","has_note":false,"prettified-request":"client","prettified-response":"client"}`, then get again, must return only `{"phase":"two"}`. After that update, `-q 'metadata:"phase"'` must return that row, and `-q '"client"'` must not, because the prettified keys are never indexed.

To prove the count, map, check, and bulk commands, capture `GET /api/one`, `GET /api/two` (`text/plain`) and `GET /logo.png` (`image/png`) from one local origin, and save the ids and `as_of` from `traffic list --json`. Then:

- `traffic count` prints `3`; `traffic count -q 'path = "/api/*"' --as-of "$AS_OF"` and `traffic count --exclude 'image/*'` print `2`; `traffic count --after "$AS_OF"` prints `0`.
- `traffic types` lists `text/plain` and `image/png` once the sitemap job is complete (`jobs list`).
- `traffic sitemap` prints the origin `http://127.0.0.1:PORT  3  0  +`. `traffic sitemap --node "http://127.0.0.1:PORT" -q 'path = "/api/*"' --as-of "$AS_OF" --json` has one child, the `/api` node, with `pairs` 2.
- `traffic sitemap --node '' --node "http://127.0.0.1:PORT" -q 'path = "/api/*"' --as-of "$AS_OF" --scope all` prints `# (origins)` with one row of `http://127.0.0.1:PORT`, 3, 0, 2, 0, `+`, then `# http://127.0.0.1:PORT` with rows `…/api` 2, 0, 2, 0, `+` and `…/logo.png` 1, 0, 0, 0. Each level's rows sit between its column-name lines. Without `--scope` the second level has only `/api`. Without `-q` the matching columns are `-`. Adding `--node 'http://nope.invalid'` prints `# http://nope.invalid (missing)` with no rows. `--json` returns `{"levels":[{"node","items","next_cursor","missing"}],"sitemap":{"complete":true}}`, each item with `matching` and `matching_errors` (`null` without `-q`). `--scope matching` without `-q`, `--scope` other than `all` or `matching`, and `--cursor` with two `--node`s each exit 1 before any request.
- `traffic validate -q 'path = "/api/*"' --exclude 'image/*' --order-by 'length desc'` exits 0. `-q 'hots = "a"'`, `--order-by colour`, and `--exclude 'not a type'` each exit 1 with `validating query: invalid_query:`, and the first ends `at position 1`. With `--json` the failure is `{"error":"validating query: invalid_query: …"}` on stdout and nothing on stderr.
- `traffic bulk metadata set triage.state '"seen"' -q 'path = "/api/*"' --as-of "$AS_OF"` prints `2 pairs updated`, and `traffic count -q 'metadata.triage.state = "seen"'` prints `2`. `traffic bulk metadata clear triage --id "$ONE" --id "$TWO" --json` returns `{"count":2}`, and `-q 'metadata.triage:*'` then counts `0`.
- The three pairs have `number` 1, 2 and 3 in capture order. `traffic list -q 'number = 2' --json` returns only `/api/two`, `-q 'number >= 2'` the last two, and `-q 'number = "2"'` fails with `invalid_query: number needs a whole number`. `traffic list --order-by number` prints 3, 2, 1 by its first column and `--order-by 'number desc'` prints 1, 2, 3, because a page's items come last display row first (see below); `--json` `items` are in the same order.
- Walk stability under `--backward`: capture three pairs, then with `checkpoint intercept on` send two more and forward each held request with `--intercept-response`, so both pairs have no response. Run `traffic list --order-by status_code --backward --limit 1 --json` (the newest pair with no response) and save `as_of` and `prev_cursor`. Forward both held responses and wait for `traffic count -q 'NOT status_code >= 0'` to print `0`. Keep walking with `--backward --limit 1 --cursor "$PREV" --as-of "$AS_OF"` until `prev_cursor` is null: the five pages hold five distinct `number`s, the second page's pair has status 200 but is read with the pairs that had none, and a fresh `traffic list --order-by status_code` lists all five by status.
- `traffic bulk delete --id "$ONE"` prints `1 pair deleted`. `traffic bulk delete -q '' --as-of "$AS_OF" --json` returns `{"count":2}`, and `traffic count` prints `0`. The next captured pair gets number 4: deleted numbers are never reused, even after the project is reopened.

## Gotchas

- Each page is the newest remaining rows, oldest first within the page. `--limit 1` is still the newest match. `next_cursor` is the oldest id of the current page when an older page remains, otherwise `null` (JSON) or absent (human stderr). Never assume a stable UUID or timestamp.
- `host = "..."` is exact, keeps case, and may include the origin port for a non-default port. A `*` at the start or end matches anything there.
- `path = "/proof*"` matches a path prefix. `status_code` also takes `<`, `<=`, `>`, and `>=`. The removed `--host`, `--method`, `--path`, and `--status-code` flags are unknown flags.
- `--order-by number` is capture order, which under concurrent capture can differ by a few places from `requested_at`. Every pair has a number; a pair an older Marasi binary captured gets one the next time this binary opens the project.
- Under `--order-by`, text sorts in byte order as stored (`host` keeps its port, uppercase before lowercase), `length` sorts numerically (20 before 100), equal values list oldest first ascending and newest first with `desc`, and pairs with no response sort last both ways. Within one walk (pages joined by `--cursor`), a pair keeps the place it had on the walk's first page: one whose response arrives mid-walk stays with the pairs with no response, under `--backward` too, so no pair is listed twice; a new `traffic list` shows it in its sorted place. A page's items still come last display row first. A cursor from another `--order-by` fails with `invalid_cursor`; an unknown field or a modifier other than `desc` (even `asc`) fails with `invalid_query` and a position.
- Human output writes `next_cursor=$NEXT_CURSOR` to stderr. JSON keeps it in `next_cursor`.
- Every `traffic list` page has `"index":{"complete":bool}`. While an opened project's older pairs are still being indexed in the background it is `false`, text conditions can miss those pairs, and human output adds a `notice:` line on stderr. A new project, or one fully indexed, is `true`. It waits for both background jobs: `traffic_index` (heads and bodies) and `annotation_index` (notes and metadata).
- Text search reads bodies decoded by their `Content-Encoding` (`gzip`, `br`, `deflate`, `zstd`, and stacked codings such as `gzip, br`), request bodies too. A body that fails to decode, or decodes past 10 MiB, is searched as stored. `traffic get` still returns the raw bytes as captured. Pairs indexed before decoding are re-decoded only by `POST /jobs/traffic_index/rebuild`.
- `traffic sitemap` reads `GET /traffic/sitemap?node=&q=&exclude=&as_of=&cursor=&limit=`; the CLI rejects `-q` without `--as-of` and `--as-of` without `-q` before any request. Human output adds a `notice:` line on stderr while the sitemap or, in query mode with text, the traffic index is still building. An empty `node` lists the origins (`scheme://host[:port]`, lowercased). Each item has `name`, `segment`, `pairs`, `errors` (5xx responses), and `has_children`, ordered by `pairs` highest first, `limit` 1 through 500 (default 100). Counts leave out the `exclude` types, and an item with no pairs left is not listed. Decimal ids, UUIDs, and 32/40/64-character hex collapse to `{int}`, `{uuid}`, and `{hash}`, so `/users/42` is under `.../users/{int}`. An unknown `node` is 404. The body has `"sitemap":{"complete":bool}`; a `traffic list` query with a `sitemap` condition carries the same object. With `q` (even empty) the read is in query mode: `as_of` is required (400 `bad_request` without it, and for `as_of` without `q`), and the counts are computed exactly over the pairs matching `q` and `exclude` with an id at or below `as_of`, so a pair captured later never changes them. The read stops when the client disconnects.
- `POST /traffic/sitemap/levels` takes `{"nodes":[…],"scope":"all"|"matching","exclusion":[…],"selection":{"query","exclusion","as_of"},"cursors":{"<node>":"<cursor>"},"limit":n}`: 1 to 64 nodes, `limit` 1 through 500 (default 100), and `as_of` required in a selection. `pairs` and `errors` are over all traffic less `exclusion`; `matching` and `matching_errors` count the subtree's pairs that the selection matches, and are `null` without one. `scope` `matching` needs a selection, and lists and orders children by their matching pairs; `all` lists and orders them by `pairs`. A malformed body, an unknown scope, or `matching` without a selection is 400 `bad_request`; a bad query is 400 `invalid_query` with a position, and a bad cursor 400 `invalid_cursor`. A node with no match is a level with `missing` true and no items, not a 404. The read stops when the client disconnects.
- A project captured by a Marasi from before ADR-0036 kept prettified copies inside metadata. On open, the `prettified_move` background job moves them out, newest pairs first, and `GET /jobs` lists it. `traffic get` returns the copies in `prettified` whether or not the pair has moved yet, and `traffic metadata get` never shows them.
- `traffic get` requires a UUID. Invalid IDs fail before repository lookup.
- `traffic metadata update` requires `--file` or piped stdin with a non-empty JSON object body. A TTY stdin fails.
- `--limit` must be 1 through 500. The default is 200.
- Metadata update replaces client-owned keys. It drops a submitted `has_note`, `prettified-request`, or `prettified-response`, leaves the pair's prettified copies unchanged because they are not metadata, and sets `has_note` to JSON boolean `true` only when a note already exists. `notes set` is a different writer: it stores `has_note` as the JSON number `1`. `traffic metadata get` omits `prettified-request` and `prettified-response`. It does not add `has_note` when no note exists.
- Bulk metadata keys are dotted like query keys (`a.b` is `b` inside `a`); a missing parent object is created, and a parent that is not an object is left alone and not counted. A key with an empty segment, `"` or `\`, or a top-level `prettified-request`, `prettified-response` or `has_note`, is a 400 `{"error":"invalid_metadata_key","message":…}` naming it. Missing `key`, or not exactly one of `value` and `"clear":true`, is 400 `invalid_bulk_request`. `"value":null` sets a JSON null.
- After `POST /traffic/bulk/delete`, `traffic get` on a deleted pair is 404, a text query on its body or note matches nothing, and the sitemap counts equal what `POST /jobs/sitemap/rebuild` would build. A sitemap node left with no pairs stays stored with zero counts until the next rebuild, so it is simply not listed. A pair deleted while in flight, or while Checkpoint holds it, can still get its response: the writer drops it with a debug log and no error, so the service log, which records Info and above, shows nothing, and no row comes back.
- A bulk command with a query selection is refused while a background job its query depends on is incomplete (`jobs list`): the search index jobs for a text term, `sitemap` for a `sitemap` condition. The route answers 409 `{"error":"selection_incomplete","message":…,"jobs":[…]}`, nothing changes, and no `traffic.changed` is published; the CLI exits 1 with `selection_incomplete`. Queries with neither, and `--id`/`--ids-file` selections, are never refused. On a small project a rebuild finishes within milliseconds, so prove it on a large project: open a 100k-pair fixture with `project open --path`, wait for `jobs list` to be all complete, then run `jobs rebuild sitemap` and immediately `traffic bulk highlight 3 -q 'sitemap != "https://nowhere.invalid"' --as-of "$AS_OF"`, which exits 1 with `selection_incomplete: … sitemap`; once `jobs list` shows `sitemap` complete the same command succeeds. `annotation_index` rebuilds a 100k fixture before the next command starts, so it cannot be caught this way.
- A response merges its metadata into the stored metadata (RFC 7396 `json_patch`) instead of replacing it, so a key set while the pair was in flight survives the response. A key cleared while the pair was in flight comes back if the response-time context still has it.
