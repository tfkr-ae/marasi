# Launches are tracked and cancellable

A launch that hung left the caller with nothing to cancel and no outcome beyond correlating `launchpad_id` in traffic events, and several GUIs can share one service instance. The proxy now keeps an in-memory registry of launches. `Launch` returns a launch id once the launch is accepted. The launch id is the UUID of the request/response pair the launch creates: the proxy client sends it in an internal `x-marasi-launch-id` header, and `SetupRequestModifier` uses it as the row id and reads the launchpad id from the registry. `x-launchpad-id` is removed. The header is honored only on a request that carries the internal client token and names a pending launch that has not been claimed yet. Any other request has the header removed and is ordinary traffic. A second claim of the same id is dropped, so nothing is sent upstream twice. Launches use a connection per launch with no keep-alive, so the transport never retries one on a reused connection.

A launch is `pending` until it is `completed`, `cancelled`, or `failed`. `cancelled` always means a user cancelled it, and a project switch, service stop, or listener stop is `failed` with reason `interrupted`, because a launch goes through the listener. Cancelling cancels the proxy client's request context. ADR-0026 carries that through the proxy, ADR-0025 fails a running hook closed, and ADR-0030 frees a Checkpoint hold. Every launch stores its request. If a launch ends before the request is written, the request is stored as launched. The pair's metadata holds a `launch` object with `status` and, for `failed`, `reason`. It is an object rather than flat dotted keys because a traffic query reads `metadata.launch.status` as a nested path. Compass runs on a launch, but its skip decision is ignored, because a launch is deliberate and must appear in its launchpad. A launch that Compass or another extension drops fails with reason `dropped`. The control API starts a launch with `POST /launchpad/{id}/launch`, which returns `{"launch_id":…,"status":"pending"}`, and adds `GET /launch`, `GET /launch/{id}`, and `POST /launch/{id}/cancel`. `GET /launch/{id}` reads the stored pair once the launch has left the registry. Cancelling a launch that has already finished returns 409 `launch_finished`. The service publishes `launch.started`, `launch.completed`, `launch.cancelled`, and `launch.failed`. `marasi launchpad launch` waits for the final launch and cancels it on interrupt unless `--detach` is given, and `marasi launchpad cancel` cancels by id. The library offers `LaunchSync` on top of the same registry, so it can be cancelled through its context.

This decision supersedes ADR-0011.

**Considered options:** pass the caller's context to a synchronous launch; a launch id separate from the pair id; store launches in the project like Armory runs; keep `x-launchpad-id`. Rejected because only the caller that started a synchronous launch could cancel it, a separate id would point at nothing in traffic and add a third id to track, a launch lasts seconds and the stored pair is the lasting record, and any proxy client could set `x-launchpad-id` to link its own traffic into a launchpad.
