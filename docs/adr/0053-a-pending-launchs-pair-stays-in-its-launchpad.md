# A pending launch's pair stays in its launchpad

While a launch is pending, its registry entry, its events and the link `writeRequest` makes all name the launchpad it was sent from. If its pair left that launchpad, a client refreshing that launchpad on `launch.completed` would miss the pair. So while a launch is pending, Marasi refuses to move its pair to another launchpad, to unlink it, to delete it, and to delete the launchpad the registry holds it for, which also covers a launch whose pair is not written yet. Reordering it within its launchpad is allowed. A selection or list of pairs that includes a pending launch is refused as a whole, with `ErrLaunchPending` wrapped in an error that lists the pending ids, and the control API answers 409 `launch_pending`. This decision supersedes the part of ADR-0034 that lets a pending launch's pair be deleted; an in-flight pair that is not a launch can still be deleted.

Only the launch registry in memory knows that a launch is pending: the `launch` object in the pair's metadata is written when the launch finishes. The guard therefore lives on `Proxy` methods, which hold the registry lock across the check and the repository transaction so that no new launch's pair can join the selection in between. The control API handlers and marasi-app both call these methods. The repository methods underneath stay unguarded.

The `launchpad_id` key that a launch writes into its pair's metadata is set once, at launch time, and no Marasi operation updates it. After a move or an unlink it may not name a launchpad the pair is in. The links are the record of membership (ADR-0032). A later change will stop storing the key in metadata and read a launch's launchpad from the database.

**Consequences:** `launchMu` is held across the repository transaction, so a long bulk delete or unlink blocks `GetLaunch`, `CancelLaunch`, `InterruptLaunches` and the writer that links a launch's pair until it commits. This is accepted because the selection guards need it: releasing the lock before the transaction would let a new launch's pair join the selection after the check.

**Considered options:** write `launch.status = pending` into metadata at launch and guard in SQL; let the repository call back into the registry; rewrite `launchpad_id` on every move. Rejected because a pair left pending by a crash could then never move or be deleted, the repository would depend on the proxy, and the key is to be removed from metadata.
