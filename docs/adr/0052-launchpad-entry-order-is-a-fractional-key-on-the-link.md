# Launchpad entry order is a fractional key on the link

Researchers reorder a launchpad's entries and move them between launchpads, so a launchpad needs an entry order that changes only when a researcher changes it. Each `launchpad_request` link holds a `position`: a string key from `roci.dev/fracdex`, the Go port of rocicorp's fractional indexing, compared byte by byte. A move writes a key between its neighbours' keys, so only the moved links change. `GetLaunchpadRequests` lists entries by `position` unless the caller passes an `orderBy`. Every link a launchpad gains goes last, after its greatest key: a Launch when its pair is written, `LinkRequestToLaunchpad`, and `LinkTraffic`, which adds its pairs in capture order. Keys are generated inside the write transaction that inserts them, and `UNIQUE (launchpad_id, position)` turns a lost race into an error rather than a tie. That index also leads with `launchpad_id`, which the primary key `(request_id, launchpad_id)` does not, so it serves the ordered read, the greatest-key lookup and the launchpad summary join. The key never leaves Marasi: clients see only the order of the list. A Go migration rebuilds the table with `position TEXT NOT NULL` and backfills each launchpad's links in `request.id` order, which is capture order because ids are UUIDv7. A launchpad's `LastStatusCode` still comes from its newest entry by capture, not from its last entry in entry order.

A move takes pair ids from a source launchpad to a target launchpad, which may be the source, before a given entry or at the end. The moved pairs keep their order in the source. A move is one transaction and is refused as a whole if a pair is not in the source, if the target is another launchpad that already holds a pair, or if the entry to place them before is not in the target or is itself being moved. It publishes one `launchpad.entries_moved` event.

**Considered options:** integer positions; a linked list of entries; keeping order on the client; jittered keys. Rejected because integer positions rewrite every later link on each move, a linked list needs a recursive read to list a launchpad and is easily corrupted by a partial write, client order breaks when several clients share one service instance, and jitter only matters with more than one writer, while SQLite has one.

**Consequences:** keys grow by about one character each time an entry is placed at the same spot. Marasi does not rebalance them. No client sees them, so a later migration can rewrite them all if they ever grow too long.
