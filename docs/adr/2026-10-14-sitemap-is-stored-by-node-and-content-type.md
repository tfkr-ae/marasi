# The sitemap is stored by node and content type

The all-traffic sitemap is a stored tree, maintained in the same transaction as the writes that change it: capturing a pair, its response, and deletes. Its top-level nodes are origins (`scheme://host[:port]`), and below them each node is one path segment, split from the escaped path with the Go standard library. Only unambiguous identifiers collapse, each into its own placeholder: `{uuid}`, `{int}` (decimal digits) and `{hash}` (hex of 32, 40 or 64 characters). There is no token or base64 guess, because that merges ordinary words. A node is named by its canonical path, such as `https://api.x.com/users/{int}/orders`, and that name is the value of the `sitemap` query field, which matches the node's subtree. Counts are subtree totals of pairs and of 5xx responses, kept per content type, so a read can leave out a content-type exclusion and still be an indexed range read. The type counts for the whole project come from the same buckets. The split and collapse rules carry a version, and a binary with new rules rebuilds the tree as a background job.

The query-mode sitemap is not stored. It is computed exactly over a selection's query, exclusion and as-of bound, one level at a time, with children paged, and it stops when the client goes away. A client can read several levels in one call, which resolves the selection once and gives each child both its all-traffic and its matching counts.

**Considered options:** counts that ignore the exclusion, so the tree disagrees with the table; counts with the exclusion computed on each read, which is too slow at a million pairs; one generic `{id}` placeholder with a token heuristic, which gives false positives; collapsing adaptively once a node has many children, which renames nodes as traffic arrives.
