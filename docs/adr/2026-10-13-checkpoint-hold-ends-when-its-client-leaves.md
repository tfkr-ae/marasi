# A Checkpoint hold ends when its client leaves

[Client disconnect cancels the request](2026-10-09-client-disconnect-cancels-the-request.md) cancels the request context when a client disconnects, but a Checkpoint hold waited only for a forward or drop, so a request or response held for a client that had left stayed in Checkpoint until someone resolved it, and every connected GUI kept showing it. An HTTP hold now also ends when its request context is cancelled, and a WebSocket message hold ends when its connection closes, whether the client or the origin closes it. A sender that sent its close frame before closing its socket has not left: an endpoint closes its socket right after its close frame (RFC 6455 7.1.1, 7.1.7). Its socket closing does not end a hold, whether the held message is that close frame or one sent before it, so neither is lost; only the other side closing ends such a hold. The item is removed and published as `checkpoint.dropped`, and the held item fails closed the same way as a user drop ([Interrupted hooks fail closed](2026-10-09-interrupted-hooks-fail-closed.md)). Removal happens under the Checkpoint lock, so exactly one of a forward, a drop, or the abandon resolves an item, and a forward or drop that wins the race stands. Cancelling a launch relies on this to free a launch held at Checkpoint ([Launches are tracked and cancellable](2026-10-13-launches-are-tracked-and-cancellable.md)).

**Considered options:** drop the Checkpoint item only when a launch is cancelled. Rejected because a browser tab closed while its request is held leaves the same ghost item, and one cancellation path through the request context covers both.
