# Traffic lists sort by any ledger column

A traffic list takes an AIP-132 `order_by` with one field and an optional `desc`: `requested_at` (the default, `desc`, served by the UUIDv7 `id`), `method`, `host`, `path`, `status_code`, `content_type` or `length`. Every one of these sorts is backed by an index on `(key, id)`. `length` is indexed as a number, through an expression over the stored `Content-Length` text. Values compare in byte order, as stored. Each column gets only one index, so ties follow the sort's direction: ascending sorts list equal keys oldest first. A pair with no response yet has no status, type or length. It sorts last in both directions, so a pair that receives its response can only move earlier, and keyset paging never returns it twice.

Paging uses keyset cursors on `(key, id)`, never offsets. The cursor is an opaque token that carries the sort, the key, the id and whether the walk has reached the pairs with no value. This replaces ADR-0001's UUID cursor. A list read can carry `as_of`, a plain bound on `id` that does not depend on the order. Every page of a set of results passes the same `as_of`, so the pages form one snapshot under any sort, and a selection keeps the meaning ADR-0033 gives it. A client finds new matches by counting the pairs that match and are newer than `as_of`, which is a short range read. A client refreshes without losing the researcher's place by reading forward and backward from the cursor of an anchor row under a new `as_of`.

**Considered options:** offset paging, which drifts while traffic is captured; two indexes per column so that ties are always newest first, at twice the insert cost; leaving some sorts without an index, which turns their first page into a sort of the whole project.

**Consequences:** each captured pair updates about seven indexes, and the insert budget becomes a regression of at most 25%. A sort combined with a common text term must sort a large match set, so it has the same looser target as unsorted common text. The planner chooses between the sort index and a sparse filter's index from statistics, so Marasi runs `PRAGMA optimize` with a bounded `analysis_limit` when it opens and closes a project, and again after every 1000 captured pairs. That refresh waits until the proxy's database writer has had no item for two seconds: run between two writes, it held the writer long enough for a WebSocket relay waiting on it to miss its close deadline. Traffic that never pauses for two seconds postpones the refresh until it does, or until the project closes. Without the periodic run, a project opened small keeps its small statistics for the whole session, and a page with two filters can read the less selective filter's index. After every run Marasi pins the FTS5 shadow tables to the planner's default of a million rows: statistics measured while a project is new made every index merge scan the whole index, so capture slowed as the project grew.

**Amendment (ticket 28):** "can only move earlier" holds only for a forward walk. A backward walk reads the pairs with no value first, so a pair that gets its response after being returned moved into the part of the walk still to be read, and was returned again. A walk now keeps every pair in the part it was in when the walk started. Responses are numbered in the order they are written, in the append-only `pair_response_order` (migration 00024); a walk's first page reads the highest number in its snapshot, and every cursor of the walk carries it. A pair whose response was written later is read with the pairs that have no value until the walk ends, and a new walk shows it in its valued place. `responded_at` cannot draw that line: it is stamped before the write waits for the connection, which can be hundreds of milliseconds behind a background job batch. The table costs one small appended row per response, and rows of deleted pairs stay. A cursor made before this change has no number and walks as before.
