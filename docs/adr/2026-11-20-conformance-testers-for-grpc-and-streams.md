# Conformance testers for gRPC and streams

Three suites score streamed pairs, each a required check on all four conformance runs from the start. Their cases include ones that deadlock when a proxy buffers, such as `ping_pong` or an origin that waits for an answer before sending its next message, so "without buffering" is a pass or a fail without timing scores. The Checkpoint runs hold and forward, or edit keeping the length, every head, stream message and trailer block of a streamed pair.

- **`grpc-client`**: grpc-go's interop client, run with `go run …@<version>` so it never enters `go.mod`, through the shim against a **grpc-java interop server** pinned by digest, over TLS with the harness's CA. grpc-go's transport is built on the same `x/net/http2` Framer and `hpack` as Marasi, so a Go server would let quirks they share cancel out, as [Conformance testers are independent and reach Marasi through a shim](2026-11-16-conformance-testers-are-independent-and-reach-marasi-through-a-shim.md) avoided with nginx.
- **`connect-client`**: the connectrpc/conformance runner, the only tester covering gRPC-Web and Connect as well as full-duplex streams over HTTP/1.1. Its runner starts the reference server and generates its own certificates, and has no proxy option, so our own small client-under-test wrapper sends the reference client through the shim, and only the **cleartext** configurations run (HTTP/1.1 and h2c by prior knowledge). If a research prototype shows the wrapper cannot work, gRPC-Web and Connect fall back to origin fixtures and grpc-go's interop server, which also serves gRPC-Web.
- **`stream-origin`**: our own origin fixtures, for what no tester checks on the origin leg: trailers-only gRPC responses, `grpc-status`, `RST_STREAM` partway through, the gRPC-Web trailers frame, server-sent events, NDJSON, gzip across a stream, a stall past the buffering threshold, and length-keeping edits.

**Amended 2026-11-20 (the `connect-client` wrapper works):** a prototype proved the wrapper path, so the fallback is not needed. The runner, `connectrpc.com/conformance` v1.0.7, is installed with `go install connectrpc.com/conformance/cmd/connectconformance@v1.0.7` and `…/cmd/referenceclient@v1.0.7` into the job's own `GOBIN`, as h2spec is, so it never enters `go.mod`. It runs with `--mode client` and a config that lists HTTP/1.1 and HTTP/2, all three protocols, `supportsH2c: true` and `supportsTls: false`. The client under test is our wrapper. It runs `referenceclient` as a child and copies its stdout back unchanged. In each length-prefixed `ClientCompatRequest` on stdin, it rewrites only `host` (field 6) to `127.0.0.1` and `port` (field 7) to a shim it starts for that reference server, and keeps every other field's bytes. Each shim sends `CONNECT` for the reference server's `host:port` and only tunnels. Marasi then sees plain HTTP/1.1 or the h2c preface inside the tunnel and routes by the tunnel's target. No runner flag is rewritten.

On the cleartext set (6,767 cases: both server implementations the runner starts, every codec and compression), the direct run through the shim passed every case. Through a launched Marasi, every case passed except Connect, gRPC and gRPC-Web full-duplex bidirectional streams over h2c (440 cases). Those time out because Marasi reads bodies whole, which is the deadlock this suite exists to catch. No cleartext case was unroutable.

Two things shape the suite:

- **One timeout ends the run.** The runner shares one client process across the run. When a case gives no result within its fixed 20 seconds, it kills the client, and every case after that is reported as not run. So the suite runs the runner once per case, as `h2-client` runs h2spec, or in batches that no hanging case shares.
- **TLS stays out.** TLS configurations are not run. The reference client trusts only `server_tls_cert`, and the runner signs the reference server's certificate itself unless `--cert` and `--key` are given. Cases with a client certificate cannot pass through an intercepting proxy at all.
