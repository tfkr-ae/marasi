# A restart hands over to a successor and rolls back if it fails

`POST /service/restart` (`marasi service restart`) lets a client move a service instance onto the installed build without leaving the service API. The instance stops its proxy listener, releases project ownership, and starts a successor from the installed build with the same name, open project, and proxy listener address (none if it was stopped). It then waits for the successor to report ready. If the successor fails or times out, the instance takes back project ownership and the listener, keeps running the old build, and emits `service.restart_failed` with the successor's log path. Clients never end up with no instance.

The proxy listener's socket and the control listener network address's socket are handed over, never released: the instance duplicates each before it stops accepting, the successor serves the duplicates, and a rollback serves them again. No other socket on the host can take the port in between, even one the kernel picked for port 0, and a connection that arrives during the handover waits in the backlog. Windows cannot pass a socket to another process, so there the sockets close and the successor, or the rollback, binds the same address again.

Only what `service start` can rebuild survives. Held checkpoint items, live WebSocket and HTTP connections, launches, and Armory runs end. A restart is refused with `409` listing held checkpoint items unless the client passes `force`. This differs from a project switch, which waits for them ([A project switch waits for held Checkpoint items and says so](2026-10-17-project-switch-waits-for-held-checkpoint-items.md)), because a restart is optional and an indefinite wait is worse for a GUI than a clear refusal. A restart is available at any time, not only after an update.

**Considered options:** no restart in the API, so users run `service stop` then `service start`; restarting without rollback; waiting for held items. Rejected because a service-only GUI could not finish an update, a failed successor would leave no instance and an unowned project, and waiting has no bound.
