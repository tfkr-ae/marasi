# Pairs are numbered in capture order

Each request/response pair gets a pair number: an integer that starts at 1, follows capture order, never changes, and is never reused, so deleted pairs leave gaps. marasi-app shows it as the ledger's `#`, and a researcher can jump to a pair with `number = 10`. The numbers live in a side table, `pair_number(number INTEGER PRIMARY KEY AUTOINCREMENT, request_id TEXT NOT NULL UNIQUE REFERENCES request(id) ON DELETE CASCADE)`. A declared `INTEGER PRIMARY KEY` is never renumbered by `VACUUM` or a table rebuild, unlike the implicit rowid that ADR-0026 warns about, and `AUTOINCREMENT` keeps a deleted number from coming back. A side table also means the backfill writes small rows instead of rewriting every `request` row and its bodies (see ADR-0035).

The number is assigned before the request event fires, not by the writer. The repository holds a counter that is seeded on open from the highest number ever issued. The capture path takes the next value and stores it on the `ProxyRequest`, and the writer inserts it explicitly. That way the live request event already carries the number. A pair whose insert fails leaves a gap. The migration numbers existing pairs in `id` order, which is capture order because ids are UUIDv7. Pairs that an older Marasi binary captures later get numbers on the next open, after the highest existing number, through the high-water mark of ADR-0039.

**Considered options:** a `number` column on `request`; deriving the number by counting; the implicit rowid. Rejected because filling a column on existing rows rewrites every row with its bodies, counts shift after deletes and under a query, and the implicit rowid can be renumbered.

**Consequences:** under concurrent capture, number order is the order in which pairs reached the capture path. That can differ by a few places from `id` order, which is the order `requested_at` sorts by. Sorting by `number` therefore uses its own index rather than `id`.
