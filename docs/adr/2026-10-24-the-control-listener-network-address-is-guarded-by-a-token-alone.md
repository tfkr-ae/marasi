# The control listener's network address is guarded by a token alone

The control listener can also be reachable at a network address, so that a GUI in a webview, or a client on another machine, can reach a service instance that it cannot reach through the socket. The socket is guarded by its owner-only file permissions. The network address is not: any local process, any web page through DNS rebinding or a cross-origin request, and any host that can route to it can connect. The control API can run Lua, change scope, and restart the instance, so whoever reaches it controls the machine. Every request to the network address must carry the instance's control token as `Authorization: Bearer`, and nothing else decides access.

Because the token travels in a header and not in a cookie, a browser never sends it on its own, and CORS has nothing to protect. The network address echoes any `Origin`, allows the `Authorization` header, never allows credentials, and answers a preflight `OPTIONS` without the token. A request whose `Host` is not the bound address is refused, so a rebound name cannot reach it. Electron renderers, browser pages, and remote clients then work without an origin list, which would differ between a dev server, `file://` (`null`), and a custom scheme. The token is never taken from a query string, because URLs end up in logs and history. A browser client reads the event stream with a `fetch` stream, not `EventSource`.

The token is read and rotated only through the socket. A client that holds the token, for example one that stole it, cannot use the network address to read the token back or to replace it and lock the owner out. Every other route, including restart, is the same on both.

The network address serves plain HTTP. A user who exposes it beyond loopback gets a warning on stderr and in the instance log, and protects the link themselves with an SSH tunnel, a VPN, or a TLS reverse proxy. The CLI's `--remote` accepts `https` for that case. TLS can be added later without changing the token or the routes.

On a remote instance, paths a client sends mean paths on the instance machine. `wordlist add` and `report template add` would otherwise move a file on the instance machine that the user never saw, so when the CLI talks to a remote instance it uploads the file's contents and then deletes the local file, which keeps "add moves the file". `project open --path` is sent unchanged, and the instance resolves `--name` in its own config dir.

**Considered options:** an origin allowlist per instance; no CORS; TLS with a leaf from the CA certificate, required off loopback; a self-signed certificate pinned by fingerprint; the token in a query parameter for `EventSource`; token routes on both listeners; `add` commands sending a path to the instance machine. Rejected because the bearer token already stops a page that lacks it, and an allowlist only adds setup that differs per build; no CORS would rule out a browser GUI; Marasi's users can secure a link themselves, and TLS is easy to add later but hard to remove once clients depend on it; query strings leak into logs; a stolen token must not be able to rotate itself; and a path the user typed on one machine would act on a file on another.
