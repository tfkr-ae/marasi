# Project switch publishes then releases

A service instance always has one open project. Changing it is one control-API operation, `POST /project/open`, which prepares the target beside the current file, refuses when an Armory run is active or the intercept queue is not empty, pauses new project-bound work, finishes already-admitted HTTP, closes live WebSockets, flushes queued writes to the old file, then publishes the new open project and releases the old one. Close-then-open was rejected because a failed second step leaves a projectless instance and lets `WriteToDB` persist work meant for the old project into the new file. `WriteToDB` keeps binding the repository at dequeue. The flush-before-publish order is what makes that safe. Modifiers do not look up an open project. The proxy listener does not stop. There is no `/project/close`.

**Considered options:** a public close route and a close-then-open swap; binding each queued write to a repository at enqueue; waiting out intercepts the way already-admitted HTTP is drained; stopping the proxy listener for the duration of a switch; copying marasi-app's cancel-and-swap dialog into the service. Rejected because a projectless gap violates the open-project invariant, enqueue binding is a larger change than the handoff needs, intercepts and Armory runs are client-owned work the open route must not finish, project and listener stay independent (ADR-0008), and the control API has no UI.
