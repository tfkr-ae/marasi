# The traffic index builds in the background

The migration only creates the contentless FTS5 table. A background build then indexes every request/response pair missing from the index, newest first, in small batches. Each batch is one transaction, capped by the size of the stored text rather than a count of pairs, so large bodies do not hold the project's single connection for seconds. A pair larger than the cap is indexed in a batch of its own. Newly captured pairs, late responses, and note or metadata changes are indexed by the traffic repository's Go write path. The build runs on every open, so the same mechanism handles the first build, resuming after a crash or a project switch, and pairs written by an older Marasi binary that has no indexing code. A project switch cancels the build between batches and waits only for the batch in flight, so the database is never closed under a write. A pair that fails to index in three batches is logged and skipped until the project is opened again, so one unreadable pair does not stall the build. Until the build finishes, traffic list responses report `index.complete: false`; skipped pairs count as finished. When it finishes, `traffic.index_complete` is announced once.

**Considered options:** backfill inside a Go migration; a saved `indexed_through` marker; SQLite triggers. Rejected because a migration backfill blocks opening a large project for minutes, a marker cannot see pairs that older binaries add later, and triggers would need the binary check and head/body split either in SQL or in a Go function that older binaries do not register.

**Consequences:** query results can be incomplete while `index.complete` is false, and text conditions never match a skipped pair. This reverses the earlier stance that queries never return partial results, because the alternative is minutes of blocked project opens. A switch waiting for the batch in flight reverses the earlier rule that a switch never waits for the build, because closing the database under a write left the project locked; a batch is capped by size, so the wait is short. A pair is skipped only for errors in its own data. A failure of the database itself, such as a lock or a full disk, is retried without counting against any pair.
