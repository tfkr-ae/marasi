# The traffic index builds in the background

The migration only creates the contentless FTS5 table and the `traffic_index_key` table that keys it. Index rows are keyed on `traffic_index_key.id`, an `INTEGER PRIMARY KEY` mapped one to one to the request id, not on the request row's implicit rowid: `request` has a `TEXT` primary key, so `VACUUM` or a migration that rebuilds the table may renumber its rowids, and the index would then match the wrong pairs. A background build then indexes every request/response pair missing from the index, newest first, in small batches. Each batch is one transaction, capped by the size of the stored text rather than a count of pairs, so large bodies do not hold the project's single connection for seconds. A pair larger than the cap is indexed in a batch of its own. Newly captured pairs, late responses, and note or metadata changes are indexed by the traffic repository's Go write path. The build runs on every open, so the same mechanism handles the first build, resuming after a crash or a project switch, and pairs written by an older Marasi binary that has no indexing code. A project switch cancels the build between batches and waits only for the batch in flight, so the database is never closed under a write. A pair that fails to index in three batches is logged and skipped until the project is opened again, so one unreadable pair does not stall the build. Until the build finishes, traffic list responses report `index.complete: false`; skipped pairs count as finished. When it finishes, `traffic.index_complete` is announced once.

**Considered options:** backfill inside a Go migration; a saved `indexed_through` marker; SQLite triggers. Rejected because a migration backfill blocks opening a large project for minutes, a marker cannot see pairs that older binaries add later, and triggers would need the binary check and head/body split either in SQL or in a Go function that older binaries do not register.

A migration that rebuilds `request` must run outside a transaction with foreign keys off, as SQLite's table rebuild procedure requires: inside goose's transaction `PRAGMA foreign_keys = OFF` does nothing, and dropping `request` cascades to its notes and index keys. Lost index keys heal, because the next build re-keys and re-indexes every pair, but lost notes do not.

**Consequences:** query results can be incomplete while `index.complete` is false, and text conditions never match a skipped pair. This reverses the earlier stance that queries never return partial results, because the alternative is minutes of blocked project opens. A switch waiting for the batch in flight reverses the earlier rule that a switch never waits for the build, because closing the database under a write left the project locked; a batch is capped by size, so the wait is short. A pair is skipped only for errors in its own data. A failure of the database itself, such as a lock or a full disk, is retried without counting against any pair. A Marasi binary from before `traffic_index_key` writes only its own `traffic_fts` table, so a pair it changes after this index has it stays searchable by its old text until a current binary writes that pair again.
