# Armory templates name their framing and hold messages as text forms

An Armory payload position in a gRPC, gRPC-Web or Connect request is a byte range in raw text today, so a payload of another length corrupts the protobuf length prefixes and the envelope around it. We decided that an Armory template records a **message framing** of its own (`grpc`, `grpc-web` or `connect`), and a template that names one has a **message-form body**: each request message in its text form under a `--- message ---` (or `--- message compressed ---`) separator. For every request a run sends, Marasi renders the payloads into the text forms, encodes each message, compresses it again when its separator says so, and wraps it in its envelope. That means base64 for gRPC-Web text, and no envelope for Connect unary (`application/proto`, `application/json`), which is stored as `connect` and told apart by its content type. Every length is computed from scratch, never patched in place. A template with no framing renders exactly as before.

A payload inside a quoted protoscope string is escaped as a protoscope string, unless its position's function chain ends in `raw`. A payload that leaves a message unable to encode is recorded on the run and not sent, and the run goes on. The template made from a captured pair is built in core from the pair's joined request and recorded framing, with `\` and `@` escaped so it renders back to the captured text. The control API, the CLI and marasi-app all use that one builder.

**Considered options:** keep the body as raw bytes and add metadata marking which byte ranges are protobuf fields (binary is not editable in a text template, and the ranges move whenever a payload changes length); detect a message-form body from the content type and a first-line separator, with no schema change (an existing template with a gRPC content type, or one that happens to start with a separator, would quietly change meaning, and deleting the separator would turn a gRPC template back into raw bytes without any error); hold each message as a separate field outside the raw request (splits one template into parts that the CLI, the control API and the app would each have to put back together).

**Consequences:** `armory_template` gains a framing column, and the control API, the CLI and `skills/marasi/SKILL.md` gain a framing field. A template whose framing does not match its content type, whose body breaks the message-form rules, or whose position marker opens and closes on different sides of a quote is refused when it is saved. Calls where the client waits for a server message before sending its next one cannot be expressed, because every request message goes out up front.
