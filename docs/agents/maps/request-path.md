# Request path

How a proxied request travels from the client socket to the origin and back, and which Marasi clients reach the origin. Names are functions and types, so search for them. For anything inside one function, read the function.

In this map, bare "upstream" means the origin, as in `GLOSSARY.md`. An **upstream proxy** is a proxy that Marasi sends traffic through on its way to the origin. It is always written in full.

Marasi serves its listener with its own HTTP/1.1 engine, `h1Engine` (`h1engine*.go`), over the codec in `internal/h1` (docs/adr/2026-11-17-marasi-owns-its-http1-wire-format.md). It keeps every message's raw lines: modifiers edit `http.Request`/`http.Response` **views**, and the engine folds their edits back into the raw lines, so what goes out and what is stored is the wire form with only the edits changed. A client connection whose TLS negotiates `h2`, or that opens with the HTTP/2 preface in cleartext (h2c by prior knowledge), is handed to the HTTP/2 engine (`h2engine*.go`, [HTTP/2](#http2)), which does the same with ordered field lists. Nothing imports Martian (repolint `martian-import`).

## Order

1. **Listener.** `(*Proxy).Listen` binds the socket, or a restart hands one over; `(*Proxy).WrapListener` and `(*Proxy).Serve` stack the listener wrappers. The raw socket is watched beneath protocol inspection and TLS (`listener.WatchedConn`), so a client that leaves is noticed while the engine is not reading it. `ProtocolMuxListener` inspects each new connection on its own goroutine, so a client that connects and sends nothing never delays the connections behind it. The proxy gives the mux no TLS config, so TLS sent straight to the listener reaches the engine unread: `h1Conn.serve` sees its first byte `0x16` (`opening`) and intercepts it as it does TLS inside a `CONNECT` (step 2), with no `CONNECT` authority, and marks its requests `https`. A connection that opens with the HTTP/2 preface (`startsPriorKnowledge`, which peeks only as far as the bytes match, so a short HTTP/1.x request is not waited on) is h2c: `c.protocol` is `h2c` and the HTTP/2 engine serves it ([HTTP/2](#http2)).
2. **Engine.** `h1Engine.serve` accepts each connection and serves it on its own goroutine as an `h1Conn`, which runs the pipeline steps itself, one request/response pair at a time, so pipelined requests are answered in order (`h1Conn.serve`). `h1Conn.readHead` reads the head with `h1.ReadRequestHead` (timeouts under [Connections](#connections)); a head the codec cannot read gets a plain 400 (`refuse`, no pair, nothing stored) and the connection closes. The codec accepts any `HTTP/1.x` version and keeps it as written. `h1Conn.carryPair` then:
   - frames the body (`h1.RequestFraming`). For an HTTP/1.1 (or later minor) request with a body and `Expect: 100-continue`, it writes Marasi's own `100 Continue` first (`expectsContinue`), so the chains see the whole request; `Expect` is kept on the way up (docs/adr/2026-11-17-marasi-answers-100-continue-itself.md);
   - reads the body whole (`readWireBody`). Ambiguous framing (CL and TE, differing lengths, a bad chunk size, any `*h1.FramingError`) marks the request **refused** (`h1engine_refuse.go`);
   - builds the view (`head.Request()`) and gives it what every request needs (`h1Conn.prepare`: client address, scheme, the connection's context, and the URL host: inside a tunnel the tunnel's authority without its default port, whatever `Host` says, otherwise `Host`; docs/adr/2026-11-19-requests-inside-a-tunnel-go-to-the-tunnels-origin.md);
   - runs the request step with the wire message (`wireRequest`), the round trip, and the response step with the origin's (`wireResponse`);
   - writes the response: the origin's goes out through `outboundResponse` (the wire head with the view's edits merged, then framed by `h1.FrameResponseBody`); Marasi's own (`pair.FromMarasi()`, a drop's empty 200) are written by net/http. A response that cannot be made into bytes for the client (`encodedForClient` or `outboundResponse` fails) is answered, before anything of it is written, with a 502 proxy error response naming the cause, and the cause is logged (`failClientLeg`).

   A `CONNECT` never enters the modifier chains. `h1Conn.connect` runs the request step with no wire message, and `baseRequest` hands it to `(*Proxy).admitTunnel` (`tunnel.go`), the one admission hook: it marks the client connection as the proxy's own when the `CONNECT` carries `proxy.Client`'s credentials, and a refused project admission closes the connection. Compass scope and the loop check refuse no tunnel; they judge each request inside it, and scope host rules match its destination, not its `Host`. The self-client mark is `clientConnection.selfClient`, typed state on the tracked client connection. An admitted tunnel gets `HTTP/1.1 200 OK` with `Content-Length: 0`; a first byte `0x16` is TLS, which `h1Conn.intercept` (`h1engine_mitm.go`) completes with a leaf from `leafIssuer` (`leaf_issuer.go`); the HTTP/2 preface is h2c by prior knowledge, for which the tunnel's origin is dialled at once in cleartext (`dialPriorKnowledgeOrigin`, `h2engine_h2c.go`, through the waypoint and the current route) and kept as `c.handshake`; anything else is plain HTTP/1.x. Either way the tunnel's requests are read on the same `h1Conn`, unless the handshake negotiated `h2` or the client is h2c: then `h1Conn.serveH2` serves the connection as HTTP/2 until it ends ([HTTP/2](#http2)). `Upgrade: h2c` is not prior knowledge: it is an HTTP/1.1 request, and a 101 to it is relayed opaquely (step 6).

   **Origin first** (docs/adr/2026-11-19-marasi-gives-the-client-the-origins-protocol.md). When the client's ClientHello arrives, `intercept`'s `GetConfigForClient` dials the origin (`dialHandshakeOrigin`): the `CONNECT` authority, or the SNI on port 443 for TLS sent straight to the listener, sent to its waypoint when it has one (`waypointOverride`), through the current route, offering the client's ALPN list in the client's order (`withOriginALPN`). The client's handshake answers with the origin's choice, or with none when the origin chose none (`clientProtocol`). The connection it dialled is the client connection's origin connection: `c.origin` for HTTP/1.1, the origin leg for HTTP/2. When the dial fails, the handshake still completes, with `http/1.1` if the client offered it and `h2` otherwise, and every request to that origin is answered with a 502 proxy error response naming the cause (`c.handshake`, checked in `originFor` and `h2Conn.sendUpstream`). The leaf issuer offers nothing by ALPN itself.
3. **Request side.** `(*Proxy).baseRequest` (`options.go`) removes the proxy's `Proxy-Authorization` and the launch ID field, reads the request body into the view (`readRequestBody`, `body.go`) and records how it ended in `pair.RequestBodyEnding`, admits project work, and builds the `Pair` holding the wire message (`pair.requestWire`). `watchClient` then watches the client socket, unless the body was cut short. A refused request skips the chain: `refuseRequest` (`proxy_error.go`) sets the pair up, answers it with a 400 proxy error response giving the cause and stores it whatever the scope; the connection closes after the 400 (`h1Conn.drain`). Otherwise the request chain runs. `WithDefaultModifierPipeline` adds, in this order:
   1. `MarasiPagesModifier` (Marasi's own pages, the browser view: `Respond`)
   2. `PreventLoopModifier` (a request to the listener itself: 502 proxy error response, not stored)
   3. `CompassRequestModifier` (scope)
   4. `SetupRequestModifier` (pair ID, metadata, route record, launch claim; removes the internal launch and Armory fields)
   5. `OverrideWaypointsModifier`
   6. `ExtensionsRequestModifier` (Lua)
   7. `CheckpointRequestModifier` (holds the request; it shows and edits the raw wire text, `h1engine_checkpoint.go`; an edit keeps the held request's destination unless its request line names a target)
   8. `WebSocketOffersModifier`
   9. `WriteRequestModifier` (capture)

   Every modifier is a `PairModifier` (`func(*Proxy, *Pair) error`) and runs in the order added; the chains are the proxy's unexported `requestModifiers` and `responseModifiers` (`ModifierGroup`), which stop at the first control or error. A modifier ends the chain early with a control on the pair (`pair.go`): `Respond` answers locally, `Drop` drops the pair (the client gets an empty 200 and nothing goes upstream), `Stop` lets the pair go on with no further modifier in this chain. A returned error means only that something broke: `failRequestChain` (`proxy_error.go`) answers the pair with a 502 **proxy error response**, which never goes upstream, carries no `Warning` header and closes the client connection. `pair_context.go` keeps the request context in step with the pair, because each registered modifier reloads the pair from it and the route dial and Lua response hooks still read it.
4. **Capture.** The request is captured by `WriteRequestModifier`, before the round trip, and the response by `WriteResponseModifier`, after the response chain. `NewProxyRequest` stores `dumpWireRequest` (the request as it goes upstream: origin form, hop-by-hop fields removed, framing fixed, with the payload, chunked coding removed) and `NewProxyResponse` stores `dumpWireResponse` (the origin's head with the chain's edits, and the payload). An HTTP/2 pair is stored in the text form of docs/adr/2026-11-19-marasi-owns-its-http2-framing.md (`h2RequestText`, `h2ResponseText`): `METHOD path HTTP/2`, then the other pseudo-header fields as `:name: value` lines in wire position, then the fields in wire order; `HTTP/2 <status>` and its fields for the response. Readers that do not know the form skip lines that start with `:` (the search index's `contentCodings`, the browser view's `storedAsHTTP1`). The stored `Length` is the stored payload's length, so a chunked response has one too. A pair built outside the engine (`NewTestPair`) and Marasi's own responses are dumped from the view (`rawhttp.Dump*`). Each pair records its **protocol** on each leg (GLOSSARY): `Pair.clientProtocol` is `h2` when the request came as an HTTP/2 wire message (`requestWire.h2`, TLS or h2c alike) and `http/1.1` otherwise, and `pair.originProtocol` is set by the engine that sends it (`originFor` for HTTP/1.1, `h2Conn.sendUpstream` for HTTP/2). `NewProxyRequest` stores both, the origin protocol being the client's until sent; `NewProxyResponse` carries the origin protocol, empty for a pair that never reached the origin, and `InsertResponse` replaces `request.origin_protocol` only when it is set (`db/migrations/00028_pair_protocols.sql`). Both queue on `DBWriteChannel`, and `(*Proxy).WriteToDB` stores them.
5. **Round trip** (`h1Conn.roundTrip`, `h1engine_pair.go`). A pair a request modifier answered goes back with its `Respond` response; a dropped pair gets an empty 200. Anything else goes to `sendUpstream`: it resolves the route, builds the outbound request (`outboundRequest`: merge the view into a copy of the wire head, `toOriginForm` keeping the path and query as written, `RemoveConnectionOptions`, then `h1.FrameRequestBody`, which sends an unchanged body exactly as read and re-frames an edited one), takes the client connection's origin connection (`originFor`, [Connections](#connections)), writes, and reads the response head. Interim responses are relayed to an HTTP/1.1 client as they arrive, less their hop-by-hop fields (`relayInterim`), except a `100`. The response body is read whole (`h1.ReadBody`); a transfer coding other than chunked is opaque bytes, and when chunked is not last the body runs until the origin closes (RFC 9112 §6.3). Unchanged, it goes to the client and storage as read with `Transfer-Encoding` kept; edited, `FrameResponseBody` sends it chunked with the codings Marasi cannot redo dropped. A 101's body is the origin connection (`originStream`), which the engine gives up. When no response comes (a dial or route failure, a write or read error, a cut-short request body), `roundTrip` calls `roundTripFailed` (a launch finishes failed; an upstream proxy failure is logged), answers with a 502 proxy error response naming the cause, and logs it once (`logProxyError`). See [Route](#route).
6. **Response side.** `(*Proxy).baseResponse` reads the view's body (`readResponseBody`, `body.go`) and records how it ended in `pair.ResponseBodyEnding`; the view keeps the wire framing (a chunked response keeps `Transfer-Encoding` and has `ContentLength` -1). It admits project work again, then the response chain runs. It runs no response modifier for a request a request modifier answered or dropped, except a proxy error response whose request was captured: that one runs the chain so it is stored with `metadata.proxy_error`, and Compass, the extensions and Checkpoint skip it because `pair.FromMarasi()` is true. A cut-short response body stops the response side with `ErrReadBody`: no response modifier runs, `captureCutShortResponse` stores what arrived with `metadata.response_body_ending` (`cut short`) when the request was stored, and the engine forwards what arrived exactly as read, less the hop-by-hop fields, and closes the client connection. `WithDefaultModifierPipeline` adds, in this order:
   1. `ResponseFilterModifier`
   2. `WebSocketPrepareModifier` (detaches a 101's origin connection from the view's body)
   3. `CompressedResponseModifier` (a body whose `Content-Encoding` is exactly `gzip` or `br` on one line is decoded, `Content-Encoding` removed, `metadata.decoded_content_encoding` and `metadata.wire_content_length` recorded; the chain and storage see the decoded body. A body that does not decode is not an error: it goes on and is stored as received, with the reason in `metadata.content_decoding_error`)
   4. `CompassResponseModifier`
   5. `ExtensionsResponseModifier` (Lua, through `callResponseHook`)
   6. `CheckpointResponseModifier`
   7. `WebSocketNegotiationModifier`
   8. `WriteResponseModifier` (capture)

   A Go response modifier that returns an error fails closed like a request one: `failResponseChain` (`proxy_error.go`) replaces the response, which may be half-edited, with a 502 proxy error response, stores it unless capture already ran, and logs the cause. Response modifiers reach the request through `pair.Request`, never `res.Request`. No modifier touches a socket. A dropped response closes the client connection. Before writing, `encodedForClient` (`h1engine_encoding.go`) puts the origin's coded bytes and `Content-Encoding`/`Content-Length` back when nothing changed the decoded body, so the client gets what the origin sent (docs/adr/2026-11-17-compressed-responses-are-transparent-on-the-wire-and-decoded-in-storage.md). When the chain has run and captured a 101, `baseResponse` calls `(*Proxy).handOffUpgrade` (`upgrade.go`): it takes the client connection through the pair's `clientHijacker` (`h1Conn.Hijack`), writes the 101 (`writeSwitch`: the wire head with the chain's edits, the bytes capture stored) and hands both connections to the registered `UpgradeHandler`, the WebSocket relay `WebSocketUpgradeHandler`. A 101 to any other protocol (h2c, a custom upgrade) has its origin connection taken out of the body before the chain runs (`detachOpaqueUpgrade`), and after the chain, even one stopped early, `relayOpaque` carries its bytes both ways unchanged, like a tunnel; the stored pair holds the 101. `readResponseBody` never reads a 101's body. A 101 that is not handed off has its origin connection closed.

## Connections

docs/adr/2026-11-17-one-origin-connection-per-client-connection.md. Code in `h1engine_pair.go`, `h1engine_route.go` and `h1engine_endings.go`.

- **One for one.** Each client connection (`h1Conn`) owns at most one origin connection (`originConn`), dialled for its first request. A request for another origin, scheme or route closes it and dials anew (`originFor`). There is no shared pool and no reuse across client connections. Launches each open a new client connection, so a new origin connection.
- **Keep-alive.** The client leg stays open when the client's head allows it (`keepAlive`), the origin connection is still open, and the response was not read until close. The origin leg closes after a response read until close or one whose head does not keep alive. Nothing adds `Connection: close`; `Connection` and the fields it names are removed on each leg (`h1.Header.RemoveConnectionOptions`), keeping an upgrade.
- **Endings.** The origin closes while the client connection waits for its next request (`watchOrigin`): the client connection closes, unless a route swap retired that origin. The origin closes after a response: the response is finished, then the client connection closes. The client leaves while its pair is in flight: the pair's context ends and `sendUpstream`'s `AfterFunc` closes the origin connection. A body the origin cuts short is forwarded as far as it got, then the client connection closes; an origin reset is passed on as a close.
- **Timeouts.** A request head must arrive within 60 seconds (`headerTimeout`), and the next request on a kept-alive connection must start within 5 minutes (`idleTimeout`). A timeout closes the connection without a response. There is no deadline on bodies, responses or Checkpoint holds. Dial and TLS handshake keep the route dial's timeouts.
- **Shutdown.** `startClose` stops taking requests and expires the read deadline of idle connections; busy ones end after their request/response pair. `waitClosed` waits for every connection. `proxy.Close` closes open WebSocket relays first.

## HTTP/2

docs/adr/2026-11-19-marasi-owns-its-http2-framing.md and docs/adr/2026-11-19-http2-transparency-is-end-to-end-for-messages-and-per-leg-for-frames.md. Code in `h2engine*.go`, on `x/net/http2.Framer` and `hpack`, not `http2.Server` or `http2.Transport`.

- **Legs.** `h2Conn` is the client leg; `h2Origin` (`h2engine_origin.go`) is the origin leg, opened on the connection the handshake dialled (`startH2Origin`: preface, SETTINGS with `ENABLE_PUSH=0` and a large window, then the origin's first SETTINGS). Each leg has its own SETTINGS, flow control (`h2Flow`), HPACK tables and stream IDs; the writer (`h2Writer`, `h2engine_flow.go`) owns a leg's framer and encoder. The client's SETTINGS carry the origin's `MAX_CONCURRENT_STREAMS` when it sent one, nothing else; never `ENABLE_CONNECT_PROTOCOL`. Marasi opens every receive window again as data arrives, since it reads bodies whole. When the origin leg cannot be opened, each request is answered with a 502 proxy error response naming the cause. For h2c (`h2engine_h2c.go`) the origin leg speaks HTTP/2 by prior knowledge on a cleartext connection: inside a `CONNECT` it is dialled before the engine starts, as the TLS handshake's is; sent straight to the listener there is no target until a request names one, so the first stream to reach `sendUpstream` dials its `:authority` (port 80 by default, `openOriginFor`, under `dialMu`), and the client gets a second SETTINGS with the origin's `MAX_CONCURRENT_STREAMS` once it is known. Requests on that connection for another authority get the `errH2Redirect` 502. `h2Conn.origin` is read through `originLeg` because of that late open.
- **Frames.** `h2Conn.frame` keeps the client's stream states (RFC 9113 §5.1) and answers frame errors itself: a stream error resets the stream, a connection error sends GOAWAY and ends the connection after reading the client's close for a moment (`fail`, `finish`). Header blocks are decoded whatever becomes of them, and their fields are not checked: a malformed request goes to the origin as it came, so the origin's answer reaches the client as it would going direct. A client opening more streams than the origin allows gets `REFUSED_STREAM`.
- **Streams.** A stream whose request is whole (END_STREAM) is carried on its own goroutine (`dispatch`, `carry` in `h2engine_stream.go`) through the request step, the round trip and the response step, so a Checkpoint hold blocks only its own stream. Each client stream has its own origin stream (`h2Origin.send`). Streams go to the origin in the order the client opened them, unless one ahead waits longer than `h2OrderWait` (`waitTurn`). The stream's context ends when either side resets it or the connection ends; `watchClient` does not watch an HTTP/2 client's socket, which the engine reads all along.
- **Messages.** A message's ordered field list (`h2Fields`, `h2engine_fields.go`), pseudo-header fields included, is its source of truth. `h2Request.request` and `h2Response.response` give the views: `:method`, `:path`, `:scheme` and `:authority` map to `Method`, the URL and `Host`, never `Header`; a malformed `:path` is kept as the URL's `Opaque`. `merge` folds the views' edits back by the HTTP/1.1 rules (unchanged names keep their fields, a changed name keeps its first position, a new name goes last in lowercase), so an unedited message goes out exactly as it came, even one that breaks RFC 9113. A body the chain changed gets its `content-length`, when it has one, set to the new length. Trailers go on as they came, and END_STREAM falls where it fell (`endsOnData`). The URL's scheme is `https`, or `http` for h2c. Inside a tunnel the URL's host is the tunnel's origin; a request a modifier sends to another origin gets a 502 proxy error response for now (`errH2Redirect`).
- **Endings.** An origin `RST_STREAM` before the response is passed on with the same code. One partway through a body: what arrived goes to the client, its stream is reset with the same code, and the pair is stored cut short. An origin GOAWAY is relayed in the client's stream IDs (`originGoAway`): client streams it left unprocessed are left unanswered, and the connection ends once the rest finish. The client's GOAWAY is relayed to the origin. A route swap (`h2Swapped`) and shutdown (`h2Close`) send the client a graceful GOAWAY; streams in flight finish on the old route, then both legs close. When the origin connection ends, the client connection ends once its streams are done. A dropped response resets its stream with `CANCEL`.

## Route

The route says how a new connection reaches the origin: directly, or through the upstream proxy that the open project selects. It is applied when the engine dials an origin connection, and nowhere else.

- **Selection.** `Proxy.SelectUpstreamProxy` sets the selection from `ProjectResources.UpstreamProxy` when a project opens, and from `PUT /upstream-proxy-selection`. It dials nothing.
- **Resolve.** The `routeResolver` (`route_resolver.go`) combines the selection with this machine's list in `marasi_config.yaml` and returns a `Route`. It reads the YAML again only when the file's modification time or size changed. `Proxy.resolveRoute` runs it before each request (`sendUpstream`) and again for each new connection (`dialOnCurrentRoute`). A hand edit, or a change from another instance sharing the config directory, therefore applies to the next request.
- **Swap.** When the resolved route differs from the current one, `Proxy.setRoute` swaps the atomic pointer. `h1Engine.routeSwapped` closes the origin connections of client connections waiting for their next request whose route is another, and a pair a swap overtook closes its own afterwards (`retireOrigin`). The client connection stays open, and its next request dials on the new route. A request never goes out on a connection of another route: `originFor` compares the connection's route with the one just resolved. A dial that a swap overtook is discarded and runs again on the new route (`dialOnCurrentRoute`). The listener keeps running. An HTTP/2 client connection on the old route gets a graceful GOAWAY instead ([HTTP/2](#http2)).
- **Dial.** `proxy.dialOrigin` (`h1engine_route.go`) dials through the `originDialer` that `Serve` stores (`originDialer.dialPlain`/`dialTLS`, `transport.go`). `Route.dial` (`route_dial.go`) is the only place each scheme is dialled. It dials the origin's address, which is the waypoint's destination when a waypoint rewrote the URL host:
  - direct: TCP to the origin;
  - `http`: TCP to the upstream proxy, then `CONNECT host:port` with `Proxy-Authorization: Basic` when the entry has credentials. Plain-HTTP origins are tunnelled with `CONNECT` too;
  - `https`: the same `CONNECT` inside TLS to the upstream proxy (`route_tls.go`);
  - `socks5`: no authentication, or username/password when the entry has credentials, with the hostname sent unresolved (`route_socks5.go`).

  Every connection is a `routedConn` that carries the route that opened it. There is no connection pool: each client connection owns its origin connection ([Connections](#connections)).
- **Origin TLS.** For an `https` request, the utls handshake (`handshakeOrigin`, `transport.go`: SNI from the request's host) runs inside the connection that `Route.dial` returned. It offers by ALPN what the dial's context carries (`originALPN`): the client's list for the handshake's origin-first dial, `http/1.1` alone for any other dial. The TLS of an HTTPS upstream proxy itself is offered `http/1.1` only (`connectOverTLS`): the client's protocol runs inside the tunnel. Both TLS legs verify against the system roots plus the entry's CA when it has one (`Route.rootCAs`, built once per route). Direct connections and other routes never trust that CA. A failed origin handshake through an upstream proxy is a `tls_verification` `*UpstreamProxyError`; any origin certificate that does not verify is a 502 proxy error response naming the cause.
- **Fail closed.** A route that cannot carry the connection, or a selection missing from this machine's list, returns an `*UpstreamProxyError` and never a direct connection. `roundTripFailed` writes one ERROR proxy log naming the pair, the upstream proxy and the cause, and the client gets a 502 proxy error response naming the cause.
- **Snapshot.** `SetupRequestModifier` puts a `core.RouteRecord` on the pair (`Pair.Route`), which reaches the dial through the request context. `recordRoute` records the route of the origin connection that carried each request, reused or not; a failed dial records the route its final attempt tried. `NewProxyResponse` copies the pair's record into `ProxyResponse.Route`, and `InsertResponse` stores it in `request.upstream_proxy_name` and `request.upstream_proxy_address`.
- **Check.** `Proxy.CheckUpstreamProxy` (`route_check.go`) resolves a named entry with a resolver of its own and dials once through a separate `newOriginDialer` fixed to that route. It sends no request and leaves the selection alone.

## Who reaches the origin

Only the engine's origin connections, dialled through `proxy.dialOrigin`, connect to the origin. `proxy.Client` sends through Marasi's own listener, so its requests run the whole path above and are captured; extensions use it. Launches and Armory requests do not go through an `http.Client`: `(*Proxy).sendRaw` (`launch_raw.go`) writes their raw text as bytes to the same listener on a new connection each (absolute form with the proxy's credentials for `http`, a `CONNECT` with them and then TLS for `https`), so the origin gets the header case, order and whitespace that were typed. `readRawRequest` reads the text with the `internal/h1` codec and rewrites only the value of each `Content-Length` line, adds one at the end only when there is none, no `Transfer-Encoding` and a body, and leaves the body's bytes alone. Every other `http.Client` in the repo is not proxy traffic: it reads a local CDP endpoint, fetches updates, or calls the control API.

## Where an outbound header comes from

Only these touch the lines a request goes upstream with:

- the sending client, which is `proxy.Client`'s transport for an extension's requests, and for a launch or Armory request the raw text as typed plus the internal fields `sendRaw` appends (`Proxy-Authorization`, `x-marasi-launch-id`, `x-armory-run-id`, `x-marasi-metadata`), which the base pipeline and `SetupRequestModifier` remove from the view, so the merge removes their lines;
- the base pipeline (`baseRequest`);
- the request modifiers, through the view or Checkpoint's raw text;
- the engine's outbound step: `toOriginForm` (the target, and `Host` set to an absolute-form target's authority, RFC 9112 §3.2.2: added when missing, its value rewritten in place when it differs), `RemoveConnectionOptions`, and `FrameRequestBody` (framing fields only when the body changed or the head had both `Content-Length` and `Transfer-Encoding`).

Names the edits leave alone keep their lines byte for byte; a changed name keeps its first line's position and spelling; a new name is appended at the end (`h1.Header.Merge`). No `Via`, `User-Agent` or `Connection` is added. An HTTP or HTTPS upstream proxy sees only the `CONNECT` and its `Proxy-Authorization`, and a SOCKS5 upstream proxy sees only its handshake.
