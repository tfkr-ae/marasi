# Request path

How a proxied request travels from the client socket to the origin and back, and which Marasi clients reach the origin. Names are functions and types, so search for them. For anything inside one function, read the function.

In this map, bare "upstream" means the origin, as in `GLOSSARY.md`. An **upstream proxy** is a proxy that Marasi sends traffic through on its way to the origin. It is always written in full.

Marasi serves its listener with its own HTTP/1.1 engine, `h1Engine` (`h1engine*.go`), over the codec in `internal/h1` (docs/adr/2026-11-17-marasi-owns-its-http1-wire-format.md). It keeps every message's raw lines: modifiers edit `http.Request`/`http.Response` **views**, and the engine folds their edits back into the raw lines, so what goes out and what is stored is the wire form with only the edits changed. A client connection whose TLS negotiates `h2`, or that opens with the HTTP/2 preface in cleartext (h2c by prior knowledge), is handed to the HTTP/2 engine (`h2engine*.go`, [HTTP/2](#http2)), which does the same with ordered field lists. Nothing imports Martian (repolint `martian-import`).

## Order

1. **Listener.** `(*Proxy).Listen` binds the socket, or a restart hands one over; `(*Proxy).WrapListener` and `(*Proxy).Serve` stack the listener wrappers. The raw socket is watched beneath protocol inspection and TLS (`listener.WatchedConn`), so a client that leaves is noticed while the engine is not reading it. `ProtocolMuxListener` inspects each new connection on its own goroutine, so a client that connects and sends nothing never delays the connections behind it. The proxy gives the mux no TLS config, so TLS sent straight to the listener reaches the engine unread: `h1Conn.serve` sees its first byte `0x16` (`opening`) and intercepts it as it does TLS inside a `CONNECT` (step 2), with no `CONNECT` authority, and marks its requests `https`. A connection that opens with the HTTP/2 preface (`startsPriorKnowledge`, which peeks only as far as the bytes match, so a short HTTP/1.x request is not waited on) is h2c: `c.protocol` is `h2c` and the HTTP/2 engine serves it ([HTTP/2](#http2)).
2. **Engine.** `h1Engine.serve` accepts each connection and serves it on its own goroutine as an `h1Conn`, which runs the pipeline steps itself, one request/response pair at a time, so pipelined requests are answered in order (`h1Conn.serve`). `h1Conn.readHead` reads the head with `h1.ReadRequestHead` (timeouts under [Connections](#connections)); a head the codec cannot read gets a plain 400 (`refuse`, no pair, nothing stored) and the connection closes. The codec accepts any `HTTP/1.x` version and keeps it as written. `h1Conn.carryPair` then:
   - frames the body (`h1.RequestFraming`). For an HTTP/1.1 (or later minor) request with a body and `Expect: 100-continue`, it writes Marasi's own `100 Continue` first (`expectsContinue`), so the chains see the whole request; `Expect` is kept on the way up (docs/adr/2026-11-17-marasi-answers-100-continue-itself.md);
   - reads the body whole (`readWireBody`), unless it passes the body threshold ([Body threshold](#body-threshold)). A request declaring a length over the threshold gets no `100 Continue` from Marasi: its `Expect` goes on and the origin answers it. Ambiguous framing (CL and TE, differing lengths, a bad chunk size, any `*h1.FramingError`) marks the request **refused** (`h1engine_refuse.go`);
   - builds the view (`head.Request()`) and gives it what every request needs (`h1Conn.prepare`: client address, scheme, the connection's context, and the URL host: inside a tunnel the tunnel's authority without its default port, whatever `Host` says, otherwise `Host`; docs/adr/2026-11-19-requests-inside-a-tunnel-go-to-the-tunnels-origin.md);
   - runs the request step with the wire message (`wireRequest`), the round trip, and the response step with the origin's (`wireResponse`);
   - writes the response: the origin's goes out through `outboundResponse` (the wire head with the view's edits merged, then framed by `h1.FrameResponseBody`); Marasi's own (`pair.FromMarasi()`, a drop's empty 200) are written by net/http. A response that cannot be made into bytes for the client (`encodedForClient` or `outboundResponse` fails) is answered, before anything of it is written, with a 502 proxy error response naming the cause, and the cause is logged (`failClientLeg`).

   A `CONNECT` never enters the modifier chains. `h1Conn.connect` runs the request step with no wire message, and `baseRequest` hands it to `(*Proxy).admitTunnel` (`tunnel.go`), the one admission hook: it marks the client connection as the proxy's own when the `CONNECT` carries `proxy.Client`'s credentials, and a refused project admission closes the connection. Compass scope and the loop check refuse no tunnel; they judge each request inside it, and scope host rules match its destination, not its `Host`. The self-client mark is `clientConnection.selfClient`, typed state on the tracked client connection. An admitted tunnel gets `HTTP/1.1 200 OK` with `Content-Length: 0`; a first byte `0x16` is TLS, which `h1Conn.intercept` (`h1engine_mitm.go`) completes with a leaf from `leafIssuer` (`leaf_issuer.go`); the HTTP/2 preface is h2c by prior knowledge, for which the tunnel's origin is dialled at once in cleartext (`dialPriorKnowledgeOrigin`, `h2engine_h2c.go`, through the waypoint and the current route) and kept as `c.handshake`; anything else is plain HTTP/1.x. Either way the tunnel's requests are read on the same `h1Conn`, unless the handshake negotiated `h2` or the client is h2c: then `h1Conn.serveH2` serves the connection as HTTP/2 until it ends ([HTTP/2](#http2)). `Upgrade: h2c` is not prior knowledge: it is an HTTP/1.1 request, and a 101 to it is relayed opaquely (step 6).

   **Origin first** (docs/adr/2026-11-19-marasi-gives-the-client-the-origins-protocol.md). When the client's ClientHello arrives, `intercept`'s `GetConfigForClient` dials the origin (`dialHandshakeOrigin`): the `CONNECT` authority, or the SNI on port 443 for TLS sent straight to the listener, sent to its waypoint when it has one (`waypointOverride`), through the current route, offering the client's ALPN list in the client's order (`withOriginALPN`). The client's handshake answers with the origin's choice, or with none when the origin chose none (`clientProtocol`). The exception is the proxy's own client offering `h2` alone (a launch or Armory request written as HTTP/2, `ownH2Only`): an origin that chose anything but `h2` is dropped as if unreachable (`refuseNonH2Origin`, `errOriginNotH2`). The connection it dialled is the client connection's origin connection: `c.origin` for HTTP/1.1, the origin leg for HTTP/2. When the dial fails, the handshake still completes, with `http/1.1` if the client offered it and `h2` otherwise, and every request to that origin is answered with a 502 proxy error response naming the cause (`c.handshake`, checked in `originFor` and `h2Conn.sendUpstream`). An HTTP/1.1 request Marasi answers itself with a response that ends the connection, such as a proxy error response to a request that loops back, never uses that origin connection: `carryPair` closes it before writing the answer, so the origin sees its end no later than the client. The leaf issuer offers nothing by ALPN itself.
3. **Request side.** `(*Proxy).baseRequest` (`options.go`) removes the proxy's `Proxy-Authorization` and the launch ID field, reads the request body into the view (`readRequestBody`, `body.go`) and records how it ended in `pair.RequestBodyEnding`, admits project work, and builds the `Pair` holding the wire message (`pair.requestWire`). `watchClient` then watches the client socket, unless the body was cut short. A refused request skips the chain: `refuseRequest` (`proxy_error.go`) sets the pair up, answers it with a 400 proxy error response giving the cause and stores it whatever the scope; the connection closes after the 400 (`h1Conn.drain`). Otherwise the request chain runs. `WithDefaultModifierPipeline` adds, in this order:
   1. `MarasiPagesModifier` (Marasi's own pages, the browser view: `Respond`)
   2. `PreventLoopModifier` (a request to the listener itself: sets the pair up and answers a 502 proxy error response, stored whatever the scope and logged)
   3. `CompassRequestModifier` (scope)
   4. `SetupRequestModifier` (pair ID, metadata, route record, launch claim; removes the internal launch and Armory fields)
   5. `OverrideWaypointsModifier`
   6. `ExtensionsRequestModifier` (Lua)
   7. `CheckpointRequestModifier` (holds the request; it shows and edits the raw wire text, `h1engine_checkpoint.go`, or an HTTP/2 request's text form, `h2engine_checkpoint.go`; an edit keeps the held request's destination unless its request line names a target)
   8. `WebSocketOffersModifier`
   9. `WriteRequestModifier` (capture)

   Every modifier is a `PairModifier` (`func(*Proxy, *Pair) error`) and runs in the order added; the chains are the proxy's unexported `requestModifiers` and `responseModifiers` (`ModifierGroup`), which stop at the first control or error. A modifier ends the chain early with a control on the pair (`pair.go`): `Respond` answers locally, `Drop` drops the pair (the client gets an empty 200 and nothing goes upstream), `Stop` lets the pair go on with no further modifier in this chain. A returned error means only that something broke: `failRequestChain` (`proxy_error.go`) answers the pair with a 502 **proxy error response**, which never goes upstream, carries no `Warning` header and closes the client connection. `pair_context.go` keeps the request context in step with the pair, because each registered modifier reloads the pair from it and the route dial and Lua response hooks still read it.
4. **Capture.** The request is captured by `WriteRequestModifier`, before the round trip, and the response by `WriteResponseModifier`, after the response chain. `NewProxyRequest` stores `dumpWireRequest` (the request as it goes upstream: origin form, hop-by-hop fields removed, framing fixed, with the payload, chunked coding removed) and `NewProxyResponse` stores `dumpWireResponse` (the origin's head with the chain's edits, and the payload). An HTTP/2 pair is stored in the text form of docs/adr/2026-11-19-marasi-owns-its-http2-framing.md (`h2RequestText`, `h2ResponseText`): `METHOD path HTTP/2`, then the other pseudo-header fields as `:name: value` lines in wire position, then the fields in wire order; `HTTP/2 <status>` and its fields for the response. Readers that do not know the form skip lines that start with `:` (the search index's `contentCodings`, the browser view's `storedAsHTTP1`). The stored `Length` is the stored payload's length, so a chunked response has one too. A pair built outside the engine (`NewTestPair`) and Marasi's own responses are dumped from the view (`rawhttp.Dump*`). Each pair records its **protocol** on each leg (GLOSSARY): `Pair.clientProtocol` is `h2` when the request came as an HTTP/2 wire message (`requestWire.h2`, TLS or h2c alike) and `http/1.1` otherwise, and `pair.originProtocol` is set by the engine that sends it (`originFor` for HTTP/1.1, `h2Conn.sendUpstream` for HTTP/2). `NewProxyRequest` stores both, the origin protocol being the client's until sent; `NewProxyResponse` carries the origin protocol, empty for a pair that never reached the origin, and `InsertResponse` replaces `request.origin_protocol` only when it is set (`db/migrations/00028_pair_protocols.sql`). Both queue on `DBWriteChannel`, and `(*Proxy).WriteToDB` stores them.
5. **Round trip** (`h1Conn.roundTrip`, `h1engine_pair.go`). A pair a request modifier answered goes back with its `Respond` response; a dropped pair gets an empty 200. Anything else goes to `sendUpstream`: it resolves the route, builds the outbound request (`outboundRequest`: merge the view into a copy of the wire head, `toOriginForm` keeping the path and query as written, `RemoveConnectionOptions`, then `h1.FrameRequestBody`, which sends an unchanged body exactly as read and re-frames an edited one), takes the client connection's origin connection (`originFor`, [Connections](#connections)), writes, and reads the response head. Interim responses are relayed to an HTTP/1.1 client as they arrive, less their hop-by-hop fields (`relayInterim`), except a `100`. The response body is read whole (`readBodyOrPass`), unless it passes the body threshold ([Body threshold](#body-threshold)); a transfer coding other than chunked is opaque bytes, and when chunked is not last the body runs until the origin closes (RFC 9112 §6.3). Unchanged, it goes to the client and storage as read with `Transfer-Encoding` kept; edited, `FrameResponseBody` sends it chunked with the codings Marasi cannot redo dropped. A 101's body is the origin connection (`originStream`), which the engine gives up. When no response comes (a dial or route failure, a write or read error, a cut-short request body), `roundTrip` calls `roundTripFailed` (a launch finishes failed; an upstream proxy failure is logged), answers with a 502 proxy error response naming the cause, and logs it once (`logProxyError`). See [Route](#route).
6. **Response side.** `(*Proxy).baseResponse` reads the view's body (`readResponseBody`, `body.go`) and records how it ended in `pair.ResponseBodyEnding`; the view keeps the wire framing (a chunked response keeps `Transfer-Encoding` and has `ContentLength` -1). It admits project work again, then the response chain runs. It runs no response modifier for a request a request modifier answered or dropped, except a proxy error response whose request was captured: that one runs the chain so it is stored with `metadata.proxy_error`, and Compass, the extensions and Checkpoint skip it because `pair.FromMarasi()` is true. A cut-short response body stops the response side with `ErrReadBody`: no response modifier runs, `captureCutShortResponse` stores what arrived with `metadata.response_body_ending` (`cut short`) when the request was stored, and the engine forwards what arrived exactly as read, less the hop-by-hop fields, and closes the client connection. `WithDefaultModifierPipeline` adds, in this order:
   1. `ResponseFilterModifier`
   2. `WebSocketPrepareModifier` (detaches a 101's origin connection from the view's body)
   3. `CompressedResponseModifier` (a body whose content codings are all `gzip`, `x-gzip`, `deflate`, `br` or `zstd`, in any case, on one field line or several, is decoded last first (`internal/contentcoding`, which the search index shares), `Content-Encoding` removed, `metadata.decoded_content_encoding` and `metadata.wire_content_length` recorded; the chain and storage see the decoded body. A body that does not decode is not an error: it goes on and is stored as received, with the reason in `metadata.content_decoding_error`)
   4. `CompassResponseModifier`
   5. `ExtensionsResponseModifier` (Lua, through `callResponseHook`)
   6. `CheckpointResponseModifier`
   7. `WebSocketNegotiationModifier`
   8. `WriteResponseModifier` (capture)

   A Go response modifier that returns an error fails closed like a request one: `failResponseChain` (`proxy_error.go`) replaces the response, which may be half-edited, with a 502 proxy error response, stores it unless capture already ran, and logs the cause. Response modifiers reach the request through `pair.Request`, never `res.Request`. No modifier touches a socket. A dropped response closes the client connection. Before writing, `encodedForClient` (`h1engine_encoding.go`) puts the origin's coded bytes and `Content-Encoding`/`Content-Length` back when nothing changed the decoded body, so the client gets what the origin sent (docs/adr/2026-11-17-compressed-responses-are-transparent-on-the-wire-and-decoded-in-storage.md). When the chain has run and captured a 101, `baseResponse` calls `(*Proxy).handOffUpgrade` (`upgrade.go`): it takes the client connection through the pair's `clientHijacker` (`h1Conn.Hijack`), writes the 101 (`writeSwitch`: the wire head with the chain's edits, the bytes capture stored) and hands both connections to the registered `UpgradeHandler`, the WebSocket relay `WebSocketUpgradeHandler`. A 101 to any other protocol (h2c, a custom upgrade) has its origin connection taken out of the body before the chain runs (`detachOpaqueUpgrade`), and after the chain, even one stopped early, `relayOpaque` carries its bytes both ways unchanged, like a tunnel; the stored pair holds the 101. `readResponseBody` never reads a 101's body. A 101 that is not handed off has its origin connection closed.

## Connections

docs/adr/2026-11-17-one-origin-connection-per-client-connection.md. Code in `h1engine_pair.go`, `h1engine_route.go` and `h1engine_endings.go`.

- **One for one.** Each client connection (`h1Conn`) owns at most one origin connection (`originConn`), dialled for its first request. A request for another origin, scheme or route closes it and dials anew (`originFor`). There is no shared pool and no reuse across client connections. Launches each open a new client connection, so a new origin connection.
- **Keep-alive.** The client leg stays open when the client's head allows it (`keepAlive`), the origin connection is still open, and the response was not read until close. The origin leg closes after a response read until close or one whose head does not keep alive. Nothing adds `Connection: close`; `Connection` and the fields it names are removed on each leg (`h1.Header.RemoveConnectionOptions`), keeping an upgrade.
- **Endings.** The origin closes while the client connection waits for its next request (`watchOrigin`): the client connection closes, unless a route swap retired that origin. The origin closes after a response: the response is finished, then the client connection closes. The client leaves while its pair is in flight: the pair's context ends and `sendUpstream`'s `AfterFunc` closes the origin connection (and, for a streamed pair, records it cancelled: [Streamed pairs](#streamed-pairs)). A body the origin cuts short is forwarded as far as it got, then the client connection closes; an origin reset is passed on as a close.
- **Timeouts.** A request head must arrive within 60 seconds (`headerTimeout`), and the next request on a kept-alive connection must start within 5 minutes (`idleTimeout`). A timeout closes the connection without a response. There is no deadline on bodies, responses or Checkpoint holds. Dial and TLS handshake keep the route dial's timeouts.
- **Shutdown.** `startClose` stops taking requests and expires the read deadline of idle connections; busy ones end after their request/response pair. `waitClosed` waits for every connection. `proxy.Close` cancels live streamed pairs and closes open WebSocket relays first (`CloseLiveTrafficAndFlush`, docs/adr/2026-11-21-project-switch-and-shutdown-cancel-live-streamed-pairs.md), so a gRPC or SSE stream does not keep `waitClosed` waiting. A streamed response goes live (`streamedPair.goLive`) only once `baseResponse` admitted its head in its request's project generation; one admitted after a switch is refused with a 502 (`passStaleResponse`) and not carried.

## HTTP/2

docs/adr/2026-11-19-marasi-owns-its-http2-framing.md and docs/adr/2026-11-19-http2-transparency-is-end-to-end-for-messages-and-per-leg-for-frames.md. Code in `h2engine*.go`, on `x/net/http2.Framer` and `hpack`, not `http2.Server` or `http2.Transport`. The `h2-client` (h2spec against nginx) and `h2-origin` (scripted fixtures, `internal/conformance/h2origin/catalogue.go`) conformance suites are required checks on all four runs, as the h1 suites are; a change on this path runs them (`make conformance SUITES=h2-origin`).

- **Legs.** `h2Conn` is the client leg; `h2Origin` (`h2engine_origin.go`) is the origin leg, opened on the connection the handshake dialled (`startH2Origin`: preface, SETTINGS with `ENABLE_PUSH=0` and a large window, then the origin's first SETTINGS). Each leg has its own SETTINGS, flow control (`h2Flow`), HPACK tables and stream IDs; the writer (`h2Writer`, `h2engine_flow.go`) owns a leg's framer and encoder. The client's SETTINGS carry the origin's `MAX_CONCURRENT_STREAMS` when it sent one, nothing else; never `ENABLE_CONNECT_PROTOCOL`. Marasi opens the connection's receive window again as data arrives. A stream's window is opened again with each DATA frame for a body read whole or passed past the body threshold, and only as the reader takes the bytes for a streamed direction ([Streamed pairs](#streamed-pairs)); the origin leg's SETTINGS give each origin stream a 1 MiB window (`h2OriginStreamWindow`) for that reason, and a large connection window. When the origin leg cannot be opened, each request is answered with a 502 proxy error response naming the cause. For h2c (`h2engine_h2c.go`) the origin leg speaks HTTP/2 by prior knowledge on a cleartext connection: inside a `CONNECT` it is dialled before the engine starts, as the TLS handshake's is; sent straight to the listener there is no target until a request names one, so the first stream to reach `sendUpstream` dials its `:authority` (port 80 by default, `openOriginFor`, under `dialMu`), and the client gets a second SETTINGS with the origin's `MAX_CONCURRENT_STREAMS` once it is known. Requests on that connection for another authority are redirected requests (below). `h2Conn.origin` is read through `originLeg` because of that late open.
- **Frames.** `h2Conn.frame` keeps the client's stream states (RFC 9113 §5.1) and answers frame errors itself: a stream error resets the stream, a connection error sends GOAWAY and ends the connection after reading the client's close for a moment (`fail`, `finish`). Header blocks are decoded whatever becomes of them, on both legs, so each leg's HPACK table stays in step (`h2Block`, `h2engine_flow.go`); their fields are not checked: a malformed request goes to the origin as it came, so the origin's answer reaches the client as it would going direct. A block longer than the HTTP/1.1 head limit (`h2MaxBlock`, 1 MiB), as read or as decoded, ends its connection with `ENHANCE_YOUR_CALM`. Closed client stream IDs are kept in a bounded record (`h2ClosedStreams`), so HEADERS on a closed stream is told from HEADERS on a skipped one among recent IDs. A client opening more streams than the origin allows gets `REFUSED_STREAM`.
- **Streams.** A stream whose request is whole (END_STREAM), or whose request head names a message framing the engine streams, or whose request body passed the body threshold ([Body threshold](#body-threshold)), is carried on its own goroutine (`dispatch`, `carry` in `h2engine_stream.go`) through the request step, the round trip and the response step, so a Checkpoint hold blocks only its own stream. Each client stream has its own origin stream (`h2Origin.send`). Streams go to the origin in the order the client opened them, unless one ahead waits longer than `h2OrderWait` (`waitTurn`). For a stream Checkpoint holds, the wait for it runs from the hold's start (`withHoldHooks`: `holdHTTP` runs `started`, and forward, drop or abandon run `ended` before the request goes on): a quick hold keeps the client's order, and a long one delays the streams behind it once, by `h2OrderWait` at most. The origin's interim responses are all relayed, less `100`; a `WINDOW_UPDATE` that overflows an origin stream's window resets that stream with `FLOW_CONTROL_ERROR` and the client gets a 502. The stream's context ends when either side resets it or the connection ends; `watchClient` does not watch an HTTP/2 client's socket, which the engine reads all along.
- **Messages.** A message's ordered field list (`h2Fields`, `h2engine_fields.go`), pseudo-header fields included, is its source of truth. `h2Request.request` and `h2Response.response` give the views: `:method`, `:path`, `:scheme` and `:authority` map to `Method`, the URL and `Host`, never `Header`; a malformed `:path` is kept as the URL's `Opaque`. `merge` folds the views' edits back by the HTTP/1.1 rules (unchanged names keep their fields, a changed name keeps its first position, a new name goes last in lowercase), so an unedited message goes out exactly as it came, even one that breaks RFC 9113. A body the chain changed gets its `content-length`, when it has one, set to the new length. Trailers go on as they came, and END_STREAM falls where it fell (`endsOnData`). Checkpoint shows a held message in the stored text form and reads an edit back with `readH2RequestText`/`readH2ResponseText` (`h2engine_text.go`): `:method`, `:path` and `:status` go back to the positions they had, and the edit's field list and body replace the wire message's, so it goes out as typed (uppercase names, `transfer-encoding`, a `content-length` that does not match), keeping the held message's trailers. Editing `:authority` or `host` changes no destination; an absolute-form request line does, and sets `:authority` to its authority. The response is written from `pair.responseWire`, which the edit replaced. A compressed response is shown decoded, without its `content-encoding`; when `encodedForClient` gives the client the coded body after all, `withCodingOf` (`h2engine_stream.go`) puts the origin's `content-encoding` back at the position it had, not last. Lua's `request:protocol()` and `response:protocol()` give `http/1.1` or `h2` from the view's `ProtoMajor`. The URL's scheme is `https`, or `http` for h2c. Inside a tunnel the URL's host is the tunnel's origin. An edit whose absolute-form request line names another origin takes the redirect path below.
- **Redirected requests.** A request a waypoint, a modifier changing the URL's host or scheme (from the connection's own, `https`, or `http` for h2c), or a Checkpoint edit sends to an origin other than the one the handshake dialled (`sendUpstream` compares the address with `originAddr` and the handshake's target) gets an origin connection of its own (`sendRedirected`, `h2engine_redirect.go`), offered the client's ALPN list (`h2` then `http/1.1` for h2c, which has none), carrying that one request and closed after its response. It does not wait its turn, so the connection's other streams go on to their origin. When the origin chose `h2` the request goes as it is on a fresh origin leg. Otherwise, and always for an `http` target, since there is no ALPN to ask, the pair is translated (`sendTranslated`): `h1RequestFromH2` writes the request line from `:method` and `:path`, a `host` from `:authority` when there is none, the `cookie` fields joined, and `content-length` (chunked when there are trailers); `h2FieldsFromH1` reads the response back with lowercase names, less the connection-specific fields. Header case is lost in translation. The pair's `originProtocol` records what it went out in, so a translated pair is stored with client protocol `h2` and origin protocol `http/1.1`.
- **Endings.** An origin `RST_STREAM` before the response is passed on with the same code. One partway through a body: what arrived goes to the client, its stream is reset with the same code, and the pair is stored cut short. An origin GOAWAY is relayed in the client's stream IDs (`originGoAway`, from `h2Conn.sent`, which records each client stream's origin stream ID as `openStream` picks it, before its head is written, so a GOAWAY that answers the head always finds it): client streams it left unprocessed are left unanswered, and the connection ends once the rest finish. The client's GOAWAY is relayed to the origin. A route swap (`h2Swapped`) and shutdown (`h2Close`) send the client a graceful GOAWAY; streams in flight finish on the old route, then both legs close. When the origin connection ends, the client connection ends once its streams are done. A dropped response resets its stream with `CANCEL`. An origin stream leaves `h2Origin.streams` once the origin ended its half and the request finished going out (`h2Origin.finish`, `requestSent`): a response ending on END_STREAM or trailers, a streamed one included, finishes it, and a request whose rest passed the threshold or that is streamed keeps it open until that carry returns. A redirected request's own connection stays open until a passed or streamed body on it went (`sendRedirected`).

## Streamed pairs

docs/adr/2026-11-20-streamed-pairs-are-recognised-from-the-head-and-other-pairs-stay-buffered.md; GLOSSARY Streamed pair, Stream message, Message framing. Both engines stream every message framing. Code in `stream/` (framing, splitter), `stream_carry.go` (what every engine shares), `h2engine_streamed.go` and `h1engine_streamed.go` (HTTP/1.1, below).

- **Framing.** Each direction is decided from its own head by its content type alone: `stream.FramingOf` holds the spec's table, and `streamedFraming` (`stream_carry.go`) says which both engines carry streamed: all of them, except `application/grpc-web-text`, read whole because its messages cannot be cut before it is decoded (base64, `stream.IsGRPCWebText`), and an `sse` or `ndjson` response whose `Content-Encoding` is not exactly one of gzip or deflate (`streamedBodyEncoding`), or that declares a `content-length` with one, read whole because recompressing it would change its length. The splitter cuts `grpc`, `grpc-web` and `connect` into 5-byte envelopes (a gRPC-Web trailers frame, flag `0x80`, and a Connect end-of-stream envelope, flag `0x02`, are stream messages too), `sse` into events at a blank line (CRLF, LF or CR line endings), and `ndjson` into lines; only the envelope framings store a flags byte. A head with END_STREAM has no body to stream and is read whole. Every other pair is an ordinary pair, read whole up to the [Body threshold](#body-threshold).
- **Heads.** A streamed request is dispatched as soon as its head is read (`headerBlock`); the request step runs with an empty body and capture stores the head. `sendOn` opens the origin stream with the head alone (`h2Origin.sendHead`). A streamed response head closes the origin stream's `headed` (`streamResponse`), so `awaitResponse` returns the head while its body still arrives; the response chain runs with an empty body, and `carryStreamedResponse` writes the head with the chain's edits, then the messages.
- **Per-direction reader.** DATA for a streamed direction goes into its `h2Inbound` (the client's in `h2Conn.data`, the origin's in `h2Origin.streamedData`) instead of the message's body. `streamedPair.carry` is the direction's one reader: it feeds what arrived to a `stream.Splitter`, which consumes no further than the end of a message, then forwards the message as the bytes it came in (`streamSink.forward`, waiting on the other leg's send window) and stores it. The inbound opens the stream's receive window by what the reader took (`h2Inbound.discard`), so a receiver that stops reading stops the sender within one message and the window. A frame past the window is `FLOW_CONTROL_ERROR`. The connection window is opened at once, so one stalled stream does not stall the others.
- **Hooks.** Between being read and being forwarded, each whole message goes through `streamedPair.handle` (`stream_message.go`): `processStreamMessageExtensions` runs `processStreamMessage` in each enabled extension but `checkpoint` (and not in the extension that sent the pair) on a `stream.LiveMessage`, the Lua `streammsg`; a drop or skip stops later extensions, and an interrupted hook drops the message. Before the hooks, a message with the envelope's compressed flag is decoded (`stream.Decompress`) when the direction's `grpc-encoding` or `connect-content-encoding` (`stream.EncodingHeader`, read from the pair's head view as `carry` starts) is gzip or deflate; any other encoding leaves the payload raw and `LiveMessage.ReadOnly`, and a hook's edit to it is ignored with a `WARN` (`readOnlyRefused`). A message that fails to decode is stored as its compressed bytes with `metadata.inflate_error`, runs no hooks, and `handle` returns a `*messageDecodeError`, so `carry` resets both legs (`INTERNAL_ERROR`, or `ENHANCE_YOUR_CALM` past the limit) after a `WARN` (`undecodable`). An unedited message goes out as its original bytes, compressed or not. An edited payload goes out in a new envelope (`stream.Envelope`) with the compressed flag cleared (`stream.Uncompressed`), so uncompressed, and is stored with `metadata.edited` and `compressed` false; a dropped message is not forwarded and is stored with `metadata.dropped`. When the direction's head that went out carries `content-length` (`declareLength`), a drop or an edit that changes the message's wire length is ignored, the message goes out as it came, and a `WARN` proxy log says why (`lengthRefused`). A message cut short runs no hooks. An injected message goes through the same steps ([Injection and cancel](#streamed-pairs)).
- **Checkpoint.** In `handle`, after the hooks and the rules above, `shouldInterceptStreamMessage` asks the `stream_intercept` switch, then checkpoint's `interceptStreamMessage` (a disabled checkpoint holds nothing). A held message is a `pendingStream` (`checkpoint_stream.go`) of kind `stream`, its payload decoded as the hooks saw it and its `text` from `stream.TextForm` with the content type its direction's head went out with (`headWentOut`), the same text Lua's `message:text()` and `GET /stream/{pair_id}/message/{id}` give; a message compressed with an encoding Marasi does not decode has none. The hold runs on the direction's reader, so nothing more is read from that sender while it lasts and the other direction flows. A forward may carry an edited payload, which goes out as a hook's edit does (`outgoing`). The hold's `refuse` vets it first: a drop, or an edit that changes the wire length, on a direction whose head declared a length is `ErrStreamLengthDeclared`, an edit of a message Marasi cannot decode is `ErrStreamReadOnly`, and the message stays held. The source's `cutOff` closes when the direction is reset or cut off, either leg's reset reaching both directions' sources, and abandons every held message of the pair (`abandonStreamPair`, `OnCheckpointAbandoned`). A message that would be held once the proxy is closing is dropped instead, since nothing would resolve it. A gRPC-Web trailers frame (`stream.IsTrailersFrame`) is held this way as a `trailer` item, its block in `Raw`, edited through `CheckpointForward.Raw`.
- **Heads and trailers.** A streamed pair's heads are held by `CheckpointRequestModifier` and `CheckpointResponseModifier` as for any pair, with an empty body: a held request head opens no origin stream, and a held response head is not written, so its direction's messages wait in the inbound while the other direction flows. A direction that ends with trailers, when `shouldInterceptTrailers` (the `stream_intercept` switch, with checkpoint enabled), holds them in `carry` before `sink.end` (`streamedPair.holdTrailers`): a `trailer` item whose `Raw` is a `name: value` line per field (`trailerBlock`). A forward with `Raw` is read back by `parseTrailerBlock` (a line with no colon is `ErrTrailerEdit` and stays held) and goes out and is stored as the direction's trailers; a drop ends the direction without trailers; an abandon cancels both legs.
- **Whole-body compression** (`stream_body_compression.go`; the 2026-11-20 amendment of docs/adr/2026-10-11-proxy-terminates-permessage-deflate-per-leg.md). A streamed `sse` or `ndjson` response with a gzip or deflate `Content-Encoding` is terminated on each leg. The engine records the origin head's coding on the body (`streamedHeadEncoding`, and `h1BodyEncoding` for an HTTP/1.1 head) and, once the head went out, both codings (`streamedPair.bodyEncodings`); `carry` wraps its source and sink (`compressedBody`) before it records them on the direction, so an injected message goes through the same compressor. `inflatingSource` inflates only as the reader peeks, so the splitter, the hooks, Checkpoint and storage see decoded messages (stored with `compressed` false) and back-pressure is unchanged; `compressingSink` compresses each forwarded message with Marasi's own compressor, in the coding of the head that went out (none when the chain removed it), flushes it, and ends the compressed stream before the direction ends. The client gets the same messages in different bytes, so an edit, a drop or a hold is safe anywhere; the stream-origin `sse-gzip-*` fixtures allow-list `client.coded[0]`. A body that cannot be inflated (corrupt, or bytes after the compressed stream's end) is stored as the compressed bytes received since the read that completed the last message, `compressed` true, with `metadata.encoding` and `metadata.inflate_error`; both legs are reset `INTERNAL_ERROR` and a `WARN` proxy log names the pair (`inflateFailed`). Inflated bytes count against the limit: a message that inflates past it is stored the same way, its `inflate_error` starting `too large`, with `too_large` and `size_seen`, and both legs are reset `ENHANCE_YOUR_CALM`.
- **Limit.** A message whose envelope declares a payload over `stream_max_message_size` (64 MiB by default), or a server-sent event or NDJSON line that passes it unended, is stored empty with `metadata.too_large` and `size_seen`, both legs are reset with `ENHANCE_YOUR_CALM`, and a `WARN` proxy log names the pair (`streamedPair.tooLarge`).
- **Endings.** A reset from either side passes on to the other leg with the same code (`rstStream` and `h2Origin.cancel` close the inbound with a `streamResetError`; the origin's `RST_STREAM` reaches the client through the response sink). A body that ends, or is reset, partway through a message forwards what arrived and stores it with `metadata.cut_short`; at a clean end `Splitter.Flush` first hands back a message the end makes whole (an NDJSON line with no LF, an event whose blank line ended in a lone CR). A streamed response's trailers end its body, not the origin stream, so the request may still go out. An origin reset or connection end after the response ended cleanly leaves the response as it ended (`h2Inbound.closeUnlessEnded`), so a gRPC origin that resets the stream after its trailers to stop the request does not cut the response, or abandon a hold of its trailers. Each direction's ending is `complete`, `cancelled` (a `CANCEL`, or the stream closed under it), `reset` with `reset_code`, or `cut short`.
- **Capture.** Stream messages are queued on `DBWriteChannel` as `*domain.StreamMessage` rows of `stream_messages` (`db/stream_repo.go`), only for a pair whose request was stored. `WriteResponseModifier` defers a streamed pair's response capture (`Pair.deferResponse`); once every streamed direction ended, `streamedPair.finish` (called by `h2Conn.dispatch` on HTTP/2 and `endStreams` on HTTP/1.1) stores the response with `metadata.streamed.request`/`.response`: `framing`, `messages`, `ending`, `reset_code` and `trailers`. The stored bodies are empty. Deleting the pair deletes its stream messages (`ON DELETE CASCADE`). The same pairs are announced (`queue`, `progress`, `direction`, `finish`): `OnStreamMessage`, `OnStreamMessageProgress`, `OnStreamedPairStarted`, `OnStreamedPairUpdated` and `OnStreamedPairEnded`, which the service publishes as events.
- **Streamed state.** GLOSSARY Streamed state. `goLive` queues a `*domain.StreamedPairRecord` with each direction recorded since its last call, so the request framing is stored once the request is admitted and the response framing once the response step admits its head (`options.go`), and announces a direction added after the start as updated; `finish` queues the endings before the response. `StreamRepository.RecordStreamedPair` writes them to `request.request_framing`, `response_framing`, `request_stream_ending` and `response_stream_ending` (db/migrations/00031_streamed_pair_state.sql), which pair reads, the `streamed` and `*_framing` query fields and `ProxyResponse.Streamed` (the `traffic.response` event) read.
- **Joined request.** `Proxy.JoinedRequest` (`stream_join.go`, route `GET /traffic/{id}/request/joined`) rebuilds a streamed pair's request body from its stored request messages for a launch: refuses while the live request direction has no ending, flushes the writer, re-envelopes each forwarded message (re-compressing a decoded one) and rewrites the head's length fields.
- **Joined SSE response.** `Proxy.OpenJoinedSSEResponse` (`stream_join.go`, route `GET /traffic/{id}/response/joined`) streams an ended SSE response as `application/octet-stream`: refuses with `ErrStreamedResponseOpen` while the SSE response direction is live or before `finish` queues its response capture, refuses non-SSE pairs with `ErrResponseNotSSE`, flushes the writer, writes the stored response head unchanged, and pages through the stored response messages incrementally to write each forwarded decoded SSE event payload in order.
- **Redirected and translated.** A redirected request on an HTTP/2 origin streams as on the main origin leg, and its connection is closed once the directions end (`h2Stream.release`). A streamed request translated to HTTP/1.1 is carried a stream message at a time (`sendTranslatedRequest`): its head goes out chunked, unless it declares a length, and its messages go through an `h1Sink`, on a goroutine of its own so the response can come while it is sent. The HTTP/1.1 origin's response is read as an ordinary body, streamed framing or not, up to the [Body threshold](#body-threshold) (`readBodyOrPass`): past it, the response goes with what arrived and `feedPassing` reads the rest's payload into an `h2Passing` as the client's window lets it. Its chunked trailers (`grpc-status` among them) go to the client as HTTP/2 trailers. Carrying a translated streamed response a message at a time is not done: the HTTP/2 engine's response carry is built on the `h2Inbound` of an HTTP/2 origin stream.
- **HTTP/1.1** (`h1engine_streamed.go`). `h1StreamedFraming` is the shared `streamedFraming` rule on the head's `Content-Type`, `Content-Encoding` and a `Content-Length` no chunked coding overrides (`h1FramingFields`). A streamed request is not read in `carryPair` (`streamedRequest` leaves its body on the client connection, behind an `h1.BodyReader`); a streamed response is spotted in `sendUpstream` before its body is read (`streamedResponse`). Either way the chain runs on the head with an empty body, as on HTTP/2, and the pair's `h1Streams` (`c.streams`) holds each streamed direction's `h1Source`. The request is carried on a goroutine of its own once its head went out (`carryStreamedRequest`), so the response can come while it is sent; the response is carried on the connection's goroutine after its head is written (`carryStreamedResponse`). `h1.BodyReader` gives a chunked, length-framed or read-until-close body's payload as it arrives and reads no further than the body, so the reader takes bytes off the socket only as it forwards them, and TCP pushes back on a sender whose receiver is slow. `h1Sink` writes each message in a chunk of its own when the head that went out is chunked, as it is otherwise, and ends a chunked body with the last chunk and the trailers. A head with `Content-Length` and no chunked coding declares a length (`declareLength`). HTTP/1.1 has no reset: a reset, a too-large message or an undecodable one closes that leg's connection (`h1Source.reset`, `h1Sink.reset`), which sets `h1Streams.cancel`, so the other direction's reader sees a cancel and the sources' `cutOff` abandons held messages. The client leaving cancels the pair: once a pair streams, `sendUpstream`'s `AfterFunc` cancels the streams before it closes the origin connection. An origin close partway through a message is `cut short`; a read-until-close body ends `complete` at the close and the client connection then closes. `endStreams`, deferred in `carryPair`, waits for the request's carry, stores the pair (`streamedPair.finish`), and keeps the connection only when both directions finished their HTTP/1.1 framing cleanly (`framedCleanly`: source at `io.EOF`, sink ended, not cancelled) and both heads keep it alive — a body whose HTTP/1.1 framing ended cleanly inside a truncated stream message stays stored as `cut short` without closing a kept-alive connection; otherwise both connections close.
- **Injection and cancel.** `stream_inject.go`. Each engine records the head that went out with `headWentOut` (content type for the text form, per-message encoding) before the direction is carried. A direction's `carry` records its `src` and `sink` on the `streamedDirection` and holds its `turn`, a channel of one, from the first byte of a message until that message went out, and from the direction's end on (`stopped`). `InjectStreamMessage` takes the turn, so an injected message lands between two of the sender's messages and, while it is handled or held, nothing more is read from that sender; waiting for the turn ends with the caller's context. It refuses a direction that is not streamed, not yet carried or ended (`ErrStreamDirectionNotStreamed`, `ErrStreamDirectionEnded`) and one whose head declared a length (`ErrStreamLengthDeclared`). `InjectStreamText` is the same with the payload given in its text form: under the turn, `encodeStreamText` encodes it with the codec of the head that went out (`stream.FromText`), and text that does not encode is refused with `ErrStreamText` before anything is processed. A Checkpoint forward's `CheckpointForward.Text` goes the same way in `forwardStream`, with the `contentType` the hold recorded on the `pendingStream`, before `refuse` vets the encoded payload; Lua's `set_text` is `LiveMessage.SetText`. `injectedMessage` envelopes the payload, compressed with the direction's `encoding` when `auto` and Marasi encodes it, and `process` (what `handle` wraps) runs the hooks and Checkpoint on it with `injected` metadata, stores it, and returns the bytes the injector sends on the sink, a chunk of its own on a chunked HTTP/1.1 leg. Live streamed pairs are found by pair ID in `Proxy.streamedPairs`, filled by the first `direction` and emptied by `finish`. `CancelStreamedPair` records each direction still going `cancelled` and resets every sink with `CANCEL`, then the sender of each direction still going, or of the only direction, so each leg is reset once: `RST_STREAM CANCEL` on HTTP/2, a closed connection on HTTP/1.1. The sources' `cutOff` abandons held messages.

## Body threshold

docs/adr/2026-11-20-streamed-pairs-are-recognised-from-the-head-and-other-pairs-stay-buffered.md. Code in `body_threshold.go`, `h1engine_threshold.go` and `h2engine_threshold.go`.

- **When.** An ordinary pair's body, in either direction, is read whole until one of these holds; from then on it is forwarded as it arrives: its head declares a length over the threshold (`h1DeclaresOver`, `h2DeclaresOver`, both `lengthOver`), so the head goes out at once with no body read; the bytes read pass the threshold; or the body stalls, no new bytes for `bodyStallWait` (2 seconds) after some arrived (`bodyStall`). `cutAtThreshold` cuts what arrived into the part kept for the view and the rest. The threshold is `body_threshold` in `marasi_config.yaml`, 64 MiB when unset (`DefaultBodyThreshold`, `Proxy.bodyThreshold`).
- **HTTP/1.1.** `readBodyOrPass` reads the body's wire bytes through `h1.WireReader`, which gives them exactly as framed and stops where the framing ends, on a goroutine (`wirePump`) so a stall is noticed. A body that passes comes back as an `h1Passing`: the bytes that arrived, then the rest from the pump. The engine writes the head and what arrived, then the rest as it comes (`forward`), with its framing as it came. A request's rest goes to the origin on its own goroutine (`sendRest`) while the response is read, so an early answer (a 413) reaches the client. After the response, the client connection carries another request only once the request body went whole to an origin that keeps its connection; otherwise it closes. A passed response finishes before the origin connection's keep-alive is judged.
- **HTTP/2.** A stream is dispatched with what arrived and the rest follows on an `h2Passing`: DATA, then trailers or END_STREAM, or the reset that cut it. The rest is held in an `h2Inbound`, as a streamed direction's body is, so the stream's receive window opens again only by what went on (a receiver that stops stops the sender; memory per direction is bounded by the window); bytes read past the threshold before the body passed, whose window was given back already, are `preload`ed. It goes on through the streamed sinks (`h2Passing.forward` with `h2OriginSink` or `h2ClientSink`). A request's rest is sent on its origin stream (`forwardRequestPass`), or to an HTTP/1.1 origin it is translated for through an `h1Sink`, chunked unless its head declares a length (`sendTranslatedRequest`); a response's on the client stream (`writeResponse`). A response that ends first leaves the origin stream open until the request's rest is sent (`h2Origin.finish`, `requestSent`), and the client stream open until then too (`awaitRequestPass`).
- **The pipeline.** The view's body is what arrived, cut to the threshold, as a `passedBody`; `readBody` gives it the ending `BodyTooLarge`. `markPassedThrough` sets `metadata.<direction>_passed_through` (true) and `metadata.<direction>_body_ending` (`too large`), so the stored pair has the body up to the threshold. The chains still run on the head. Checkpoint does not hold a passed message, and a Lua body edit of one is undone (`keepPassedBody`); each is named in a WARN proxy log (`logPassedThrough`) linked to the pair by `request_id`. A request-side log is held on the pair until the request chain ends (`writeHeldLogs`, run by `baseRequest`), because the link is a foreign key and the request is stored only by `WriteRequestModifier`; a request the chain did not store names its ID only in the log's context. `CompressedResponseModifier` leaves a passed body coded. The client socket is not watched for a passed request (`watchClient`): its body is still being read.

## Route

The route says how a new connection reaches the origin: directly, or through the upstream proxy that the open project selects. It is applied when the engine dials an origin connection, and nowhere else.

- **Selection.** `Proxy.SelectUpstreamProxy` sets the selection from `ProjectResources.UpstreamProxy` when a project opens, and from `PUT /upstream-proxy-selection`. It dials nothing.
- **Resolve.** The `routeResolver` (`route_resolver.go`) combines the selection with this machine's list in `marasi_config.yaml` and returns a `Route`. It reads the YAML again only when the file's modification time or size changed. `Proxy.resolveRoute` runs it before each request (`sendUpstream`) and again for each new connection (`dialOnCurrentRoute`). A hand edit, or a change from another instance sharing the config directory, therefore applies to the next request.
- **Swap.** When the resolved route differs from the current one, `Proxy.setRoute` swaps the atomic pointer. `h1Engine.routeSwapped` closes the origin connections of client connections waiting for their next request whose route is another, and a pair a swap overtook closes its own afterwards (`retireOrigin`). The client connection stays open, and its next request dials on the new route. A request never goes out on a connection of another route: `originFor` compares the connection's route with the one just resolved. A dial that a swap overtook is discarded and runs again on the new route (`dialOnCurrentRoute`). The listener keeps running. An HTTP/2 client connection on the old route gets a graceful GOAWAY instead ([HTTP/2](#http2)).
- **Dial.** `proxy.dialOrigin` (`h1engine_route.go`) dials through the `originDialer` that `Serve` stores (`originDialer.dialPlain`/`dialTLS`, `transport.go`). `Route.dial` (`route_dial.go`) is the only place each scheme is dialled. It dials the origin's address, which is the waypoint's destination when a waypoint rewrote the URL host:
  - direct: TCP to the origin;
  - `http`: TCP to the upstream proxy, then `CONNECT host:port` with `Proxy-Authorization: Basic` when the entry has credentials. Plain-HTTP origins are tunnelled with `CONNECT` too;
  - `https`: the same `CONNECT` inside TLS to the upstream proxy (`route_tls.go`);
  - `socks5`: no authentication, or username/password when the entry has credentials, with the hostname sent unresolved (`route_socks5.go`).

  Every connection is a `routedConn` that carries the route that opened it. There is no connection pool: each client connection owns its origin connection ([Connections](#connections)).
- **Origin TLS.** For an `https` request, the utls handshake (`handshakeOrigin`, `transport.go`: SNI from the request's host) runs inside the connection that `Route.dial` returned. It offers by ALPN what the dial's context carries (`originALPN`): the client's list for the handshake's origin-first dial, `http/1.1` alone for any other dial. The TLS of an HTTPS upstream proxy itself is offered `http/1.1` only (`connectOverTLS`): the client's protocol runs inside the tunnel. Both TLS legs verify against the system roots plus the entry's CA when it has one (`Route.rootCAs`, built once per route). Direct connections and other routes never trust that CA. A failed origin handshake through an upstream proxy is a `tls_verification` `*UpstreamProxyError`; any origin certificate that does not verify is a 502 proxy error response naming the cause.
- **Fail closed.** A route that cannot carry the connection, or a selection missing from this machine's list, returns an `*UpstreamProxyError` and never a direct connection. `roundTripFailed` writes one ERROR proxy log naming the pair, the upstream proxy and the cause, and the client gets a 502 proxy error response naming the cause.
- **Snapshot.** `SetupRequestModifier` puts a `core.RouteRecord` on the pair (`Pair.Route`), which reaches the dial through the request context. `recordRoute` records the route of the origin connection that carried each request, reused or not; a failed dial records the route its final attempt tried. `NewProxyResponse` copies the pair's record into `ProxyResponse.Route`, and `InsertResponse` stores it in `request.upstream_proxy_name` and `request.upstream_proxy_address`.
- **Check.** `Proxy.CheckUpstreamProxy` (`route_check.go`) resolves a named entry with a resolver of its own and dials once through a separate `newOriginDialer` fixed to that route. It sends no request and leaves the selection alone.

## Who reaches the origin

Only the engine's origin connections, dialled through `proxy.dialOrigin`, connect to the origin. `proxy.Client` sends through Marasi's own listener, so its requests run the whole path above and are captured; extensions use it. Launches and Armory requests do not go through an `http.Client`: `(*Proxy).sendRaw` (`launch_raw.go`) writes their raw text as bytes to the same listener on a new connection each (absolute form with the proxy's credentials for `http`, a `CONNECT` with them and then TLS for `https`), so the origin gets the header case, order and whitespace that were typed. `readRawRequest` reads the text with the `internal/h1` codec and rewrites only the value of each `Content-Length` line, adds one at the end only when there is none, no `Transfer-Encoding` and a body, and leaves the body's bytes alone. Text whose request line ends `HTTP/2` is read instead in the stored text form (`readH2RawRequest`, `launch_h2.go`, on `readH2RequestText`), which adds only `:scheme` when missing and recalculates nothing; `sendRaw` sends it with `sendH2Raw` on stream 1 of a new HTTP/2 connection, through a `CONNECT` with the credentials and then TLS offering `h2` alone (`connectRaw` fails unless the proxy chose `h2`), or prior knowledge in the plain tunnel for `http`. The internal fields go last, in lowercase. A launch cancelled over HTTP/2 resets stream 1 with `CANCEL` before its connection closes (`h2LaunchClient.cancel`, run by `sendRaw`'s `AfterFunc`), so the engine passes the reset on to the origin stream rather than only ending the origin leg. An Armory template with a message framing (`ArmoryTemplate.Framing`, a message-form body) is turned into wire bytes before it reaches `sendRaw`: `encodeMessageForm` (`armory/message_form.go`) encodes each message's text form with `stream.FromText` and wraps it in a fresh envelope, so `sendRaw` sees an ordinary raw request. A launch whose head names a message framing needs nothing of its own: the engine carries it as a streamed pair ([Streamed pairs](#streamed-pairs)), its body as typed being the request's messages, and `sendRaw` reads the response to its end and waits for the engine's connection handler to return (`clientConnection.served`) once it closes the socket, so a streamed pair has finished and queued its deferred response before the launch or Armory request ends. There is no fallback: the handshake's `ownH2Only` (`h1engine_mitm.go`) sees the proxy's own client offering `h2` alone, and `refuseNonH2Origin` drops an origin that chose anything else, so the handshake completes with `h2` and the launch gets a 502 naming `errOriginNotH2`; an origin that refuses the TLS handshake or the h2c preface gets the same 502 with its own cause. Every other `http.Client` in the repo is not proxy traffic: it reads a local CDP endpoint, fetches updates, or calls the control API.

## Where an outbound header comes from

Only these touch the lines a request goes upstream with:

- the sending client, which is `proxy.Client`'s transport for an extension's requests, and for a launch or Armory request the raw text as typed plus the internal fields `sendRaw` appends (`Proxy-Authorization`, `x-marasi-launch-id`, `x-armory-run-id`, `x-marasi-metadata`), which the base pipeline and `SetupRequestModifier` remove from the view, so the merge removes their lines;
- the base pipeline (`baseRequest`);
- the request modifiers, through the view or Checkpoint's raw text;
- the engine's outbound step: `toOriginForm` (the target, and `Host` set to an absolute-form target's authority, RFC 9112 §3.2.2: added when missing, its value rewritten in place when it differs), `RemoveConnectionOptions`, and `FrameRequestBody` (framing fields only when the body changed or the head had both `Content-Length` and `Transfer-Encoding`).

Names the edits leave alone keep their lines byte for byte; a changed name keeps its first line's position and spelling; a new name is appended at the end (`h1.Header.Merge`). No `Via`, `User-Agent` or `Connection` is added. An HTTP or HTTPS upstream proxy sees only the `CONNECT` and its `Proxy-Authorization`, and a SOCKS5 upstream proxy sees only its handshake.
